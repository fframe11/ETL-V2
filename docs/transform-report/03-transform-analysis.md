# ส่วนที่ 2: วิเคราะห์ Transform — ควรปรับอะไร ควรเน้นอะไร

เอกสารนี้ตอบโจทย์ส่วนที่ 2 ของเพื่อน และข้อกำหนดเพิ่มที่ว่า **ในหน้าที่เกี่ยวกับ Transform ให้หาว่าจุดไหนดูเป็น black box แล้วทำให้เป็น white box โดยไม่ใช่การเขียนคำอธิบายเพิ่มหรือเนื้อหาให้อ่านลงในเว็บ** ข้อเท็จจริงทุกข้อมาจากเอกสาร `01-interactive-rules.md`, `02-spark-table-rules.md` และหลักฐานใน `docs/transform-report/evidence/` (รหัส S1–S10 คือสถานการณ์ในไฟล์ `interactive-scenarios.json`)

## นิยาม black box / white box ที่ใช้ในรายงานนี้

- **Black box:** จุดที่ผู้ใช้เปลี่ยนค่าหรืออ่านผลแล้ว **ไม่สามารถเห็นจากระบบเอง** ว่าระบบทำอะไรไป เช่น ตั้งค่าแล้วไม่รู้ว่าค่าไปมีผลตรงไหน ตัวเลขบนจอมาจากไหน แถวนี้ถูกตัดสินเพราะกฎข้อไหนและค่าจริงเท่าไร หรือช่องที่ตั้งได้แต่ไม่มีผลเลย
- **White box:** ผู้ใช้ตามรอยได้ครบสาย **ค่ากฎ → การคำนวณ → แถวที่โดน → ไฟล์ผลลัพธ์** ด้วยสิ่งที่ระบบแสดงหรือบันทึกเอง
- **ข้อกำหนดของงานนี้:** ห้ามแก้ด้วยการเพิ่มข้อความอธิบาย เช่น ไอคอน `?` ข้อความช่วยเหลือ แบนเนอร์ หรือหน้าคู่มือ วิธีที่ยอมรับคือ **ให้ระบบแสดงการทำงานของตัวเองออกมา** ด้วยกราฟ ตัวอย่างผลก่อนใช้จริง การเจาะลงไปดูแถว คอลัมน์ข้อมูลแบบแยกช่อง การบันทึกค่าที่ใช้จริง หรือการเอาสิ่งปลอมออก
- **หมายเหตุเรื่องงานก่อนหน้า:** ไอคอน `?` (InfoHint) และแบนเนอร์ที่เพิ่มในรอบแก้ป้ายก่อนหน้า เป็น "ข้อความ" จึง **ไม่นับ** เป็นการทำให้เป็น white box ตามข้อกำหนดนี้ ทีมต้องตัดสินใจว่าจะเก็บหรือเอาออกเมื่อทำแบบใหม่เสร็จ

## ควรเน้นอะไร

เมื่อนำเสนอ Transform ให้เน้น 5 ข้อนี้ ซึ่งมาจากสิ่งที่พิสูจน์ได้ในรายงานนี้:

1. **ตามรอยได้ตลอดสาย: ค่ากฎ → ตัวเลข → แถว → ไฟล์** (BB-06, 11, 25, 30) เป็นแกนของคำถามข้อ 2 และ 3 ของเพื่อน
2. **ตัวเลขหนึ่งตัว มีแหล่งเดียว** วงกลม 95 เทียบตาราง 93.7 (BB-08), ป้าย 12.0h เทียบรั้วจริง 23.0h (BB-09), การ์ดสรุปตัวคูณ 1.5 เทียบกฎ 3.0 (BB-04) ต่างเป็นสองตัวเลขสำหรับเรื่องเดียวกัน
3. **ไม่มีช่องที่ตั้งแล้วไม่มีผล** ฟอร์ม Spark มี 8 ช่อง ใช้ตัดสินจริง 3 ช่อง (BB-20) และตัวเลือกที่มีจริงแต่ไม่มีช่อง (BB-14)
4. **ระบบสองเอนจินที่พฤติกรรมต่างกัน ต้องแสดงตัวตนของแต่ละอันตรงๆ** (BB-28) ฝั่งการ์ดส่งค่าผิดปกติไป Review ส่วน Spark กักกันตรงๆ ฝั่งการ์ดตัดแถวซ้ำเป็นกักกัน ส่วน Spark ลบทิ้ง
5. **บันทึกสิ่งที่รันจริง ไม่ใช่สิ่งที่ตั้งไว้** (BB-19) `rules_mode = adaptive` ทั้งที่ใช้ค่าฐาน คือตัวอย่างของระบบที่รายงานสิ่งที่ตั้งไว้แทนสิ่งที่เกิดขึ้น

## ข้อที่ตรวจแล้วไม่จริง

ข้อสันนิษฐานที่ตั้งไว้ก่อนตรวจโค้ด แล้วพบว่าไม่จริง จึงไม่นำมาเป็นหัวข้อในตารางข้างบน:

1. **"ตามรอยจากตัวเลขไปหาแถวไม่ได้เลย"** ไม่จริงทั้งหมด หน้า Data Ingestion มีปุ่มดูตัวอย่าง 5 แถวต่อประเด็น (`ui/src/pages/Ingestion.jsx:138-152`) และ funnel บนหน้า Pipeline กดแล้วกรองโซนได้ (`ui/src/pages/Pipeline.jsx:284-288`) ที่ขาดคือหน้า Rule เอง (BB-11)
2. **"หน้าเว็บไม่มีตัวเลขอัตราผ่านที่คำนวณจริง"** ไม่จริง ตารางสรุปใต้การ์ดคำนวณจริงจากผลรัน (`ui/src/pages/RulesConfig.jsx:602-603`) ปัญหาคือมัน **ขัดกับวงกลมตายตัว** บนหน้าเดียวกัน (BB-08)
3. **"หน้า Data Ingestion ไม่บอกเลยว่าไฟล์ขาดคอลัมน์"** ไม่จริง มีข้อความบอกรายชื่อคอลัมน์ที่ขาด (`ui/src/pages/Ingestion.jsx:865`) แต่เป็นข้อความ และไม่มีทางแก้ในหน้านั้น (BB-01)

## แก้ไขจากคำตอบในแชทก่อนหน้า

คำตอบก่อนหน้าในแชทมีข้อที่ตรวจโค้ดแล้วไม่ตรงกับความจริง ดังนี้ (สองข้อแรกอยู่ใน `02-spark-table-rules.md` ด้วย)

1. **เคยตอบว่า** เกณฑ์ที่ Spark ใช้จริง "ไม่ได้บันทึกไว้" **ความจริง:** บันทึกทุกรอบ (`spark/spark_quality_engine.py:2823-2830`) จุดบอดคือหน้าเว็บไม่แสดง (BB-17)
2. **เคยตอบว่า** ตัวตรวจ `value_range` แบบ adaptive ตั้งแล้วไม่มีผล **ความจริง:** ตัวตรวจ IQR ทำงานจริง ช่องที่ไม่มีผลคือ `null_checks`
3. **เคยตอบว่า** ระบบคำนวณเกณฑ์ adaptive ใหม่ทุกรอบจากประวัติ 15 รอบ **ความจริง:** โค้ดเขียนไว้แบบนั้น แต่ในระบบที่ deploy อยู่ **ไม่เคยทำงาน** ทุกรอบใช้ค่าฐาน (BB-18)
4. **เคยเสนอให้** เปลี่ยนวงกลม 95/99/99 เป็น "% ที่ผ่านกฎข้อนั้นจริง" เหมือนยังไม่มีตัวเลขจริงในหน้า **ความจริง:** มีตัวเลขจริงในตารางใต้การ์ดแล้ว งานคือทำให้ตรงกัน ไม่ใช่สร้างใหม่ (BB-08)
5. **เคยเสนอให้** เพิ่มการเจาะดูแถวจากตัวเลข เหมือนทั้งระบบไม่มี **ความจริง:** มีอยู่ที่หน้า Ingestion และ funnel ที่หน้า Pipeline งานที่เหลือคือหน้า Rule (BB-11)
