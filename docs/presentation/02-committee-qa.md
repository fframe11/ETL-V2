# คำถามที่กรรมการน่าจะถาม และแนวทางตอบ

> เอกสารคู่กัน: [01-system-explainer.md](01-system-explainer.md) · [03-rubric-scorecard.md](03-rubric-scorecard.md)
> คำถามรายฟีเจอร์เชิงลึกมีอยู่ท้ายทุกบทใน `docs/whitebox-report/` (หัวข้อ "คำถามกรรมการ")

## หลักการตอบ 4 ข้อ

1. **ตอบด้วยตัวเลขและชี้ไฟล์หลักฐาน** ทุกตัวเลขในสไลด์ต้องเปิดไฟล์ใน `docs/evaluation/evidence/` ให้ดูได้
2. **จุดอ่อนให้พูดเองก่อน** โครงสร้างคำตอบ: ยอมรับ → ตัวเลขที่วัดได้ → สาเหตุ → ทางแก้ที่รู้แล้ว การถูกจับได้เสียคะแนนมากกว่าการบอกเอง
3. **แยกให้ชัดว่าอะไรวัดแล้ว อะไรยังไม่วัด** อย่าใช้คำว่า "รองรับ Terabytes" หรือ "แม่นยำ 100%" ถ้าไม่มีการวัด
4. **ไม่รู้ให้บอกว่าไม่รู้** แล้วบอกว่าจะตรวจจากไฟล์ไหน

## ก. ภาพรวมและแรงจูงใจ

**1. ระบบนี้คืออะไร ต่างจาก ETL ทั่วไปตรงไหน**
ETL ที่มีด่านตรวจคุณภาพเป็นแกน ข้อมูลทุกแถวต้องผ่าน 21 ขั้นก่อนถึงโซนใช้งาน แถวที่ไม่ผ่านถูกเก็บพร้อมเหตุผล ETL ทั่วไปย้ายและแปลงข้อมูล แต่ไม่บอกว่าแถวไหนเชื่อไม่ได้และเพราะอะไร

**2. ต่างจาก Great Expectations / Deequ / Soda อย่างไร**
เครื่องมือเหล่านั้นเป็นไลบรารีตรวจกฎ ต้องเขียนกฎเองและต่อเข้ากับ pipeline เอง ระบบนี้รวมครบวงจรในชุดเดียว: นำเข้า 4 ชนิด, ตรวจ, แยกโซนกักกัน, ประตูอนุมัติ schema, หน้าเว็บ และเพิ่มสามอย่าง: เหตุผลรายแถวที่คนอ่านเข้าใจ, เอนจินโต้ตอบสำหรับลองกฎก่อนใช้จริง, รองรับวันที่ พ.ศ. และข้อความไทยไม่เว้นวรรค
*ระวัง:* อย่าอ้างว่าดีกว่า ยังไม่เคยวัดเทียบกัน ให้พูดว่า "ต่างที่ขอบเขต"

**3. ทำไมใช้ 16 container กับข้อมูลหลักหมื่นแถว**
ยอมรับว่าเกินขนาดข้อมูลทดสอบ เส้นทางหลักใช้ 8 ตัว อีก 8 ตัวเป็นส่วนเสริมที่ปิดได้ด้วย `COMPOSE_PROFILES` (ประหยัด RAM ราว 6.9 GB) เลือกสถาปัตยกรรมนี้เพื่อให้ขยายได้ และวัดแล้วที่ 1 ล้านแถว

**4. ทำไม HDFS + Spark ไม่ใช้ pandas หรือ PostgreSQL**
pandas ต้องโหลดทั้งไฟล์เข้าหน่วยความจำเครื่องเดียว ระบบมีเอนจิน pandas อยู่แล้วสำหรับไฟล์เล็ก (เอนจินโต้ตอบ) ส่วน Spark แบ่งงานได้ และ Delta Lake ให้ MERGE ตามคีย์กับการเขียนแบบ transaction
*ถ้าถูกถามต่อว่า "มี worker ตัวเดียว ขนานจริงหรือ":* ตอนนี้ 1 worker 2 คอร์ บนเครื่องเดียว ยังไม่ได้ทดสอบหลายเครื่อง

**5. ทำไมเก็บผลใน Elasticsearch ไม่ใช่ PostgreSQL**
เอกสารผลแต่ละตารางมีโครงสร้างต่างกัน (เหตุผลกักกันต่างกัน) และ dashboard ต้องรวมผลข้ามรอบ Elasticsearch ทำสองอย่างนี้ได้โดยไม่ต้องออกแบบ schema ล่วงหน้า ข้อเสีย: ไม่มี transaction และเป็นจุดล้มจุดเดียวของระบบ (lock ก็อยู่ที่นี่)

## ข. แหล่งข้อมูลและปริมาณ (เกณฑ์ 10 คะแนน)

**6. มีแหล่งข้อมูลกี่แหล่ง ใช้จริงกี่แหล่ง**
ตัวเชื่อม 4 ชนิด: ไฟล์ CSV/Excel, REST API, PostgreSQL, Reddit ผ่าน Kafka ทั้ง 4 ผ่านการทดสอบกับระบบจริง (รายงานทดสอบ T2–T5) ให้เปิดตาราง "การนำเข้าจริงแยกตามชนิดแหล่ง" ใน `docs/evaluation/rubric-mapping.md` (มีหลังทำ Task 2)
*พูดตรงๆ:* ปริมาณส่วนใหญ่มาจากไฟล์ แหล่ง API ที่ใช้ทดสอบมี 11 ระเบียนเพราะชุดข้อมูลต้นทางมีเท่านั้น

**7. ข้อมูลเป็นของจริงหรือสร้างขึ้น**
ผสม ชุดวัดความแม่นยำ (คะแนนนักศึกษา 10,100 แถว) เป็นชุดสังเคราะห์ที่ใส่ปัญหาโดยเจตนา เพราะต้องรู้คำตอบที่ถูกจึงจะวัด precision/recall ได้ ชุดจริงที่ใช้ทดสอบปริมาณและความทนทาน: customer churn (Kaggle, 440,833 แถว), global e-commerce (2,000), grocery sales (Excel, 561), data.go.th (11), Reddit r/python (โพสต์สาธารณะ)

**8. 3.58 ล้านแถวมาจากไหน**
ผลรวมจำนวนแถวของทุกรอบที่ Spark ประมวลผล (183 รอบ) รวมรอบ benchmark 10K/100K/500K/1M ซึ่งเป็นสำเนาของชุดประเมิน และรอบที่รันตารางเดิมซ้ำ ข้อมูลที่ไม่ซ้ำกันจริงมีราว 4.5 แสนแถว (ส่วนใหญ่คือ churn 440,833 แถว)

**9. ทำไมไม่รวมข้อมูลหลายแหล่งเข้าด้วยกัน**
เส้นทาง Spark ออกแบบให้แต่ละแหล่งเป็นตารางของตัวเอง เพราะเป้าหมายคือรับรองคุณภาพรายตาราง การ join 2 ตาราง (คะแนน + ข้อมูลนักศึกษา จับคู่คีย์ได้ 99.8%) มีในเอนจินโต้ตอบ ยอมรับว่าการรวมหลายแหล่งในเส้นทาง Spark เป็นงานที่ยังไม่ได้ทำ

## ค. กระบวนการ (เกณฑ์ 15 คะแนน)

**10. 21 กระบวนการนับอย่างไร ทุกตัวทำงานจริงไหม**
นับจาก stage ที่ลงทะเบียนในโค้ด พิมพ์รายการได้ด้วยคำสั่งเดียว (`python -m sdoqap.pipeline --json`) จัดเป็น 5 กลุ่ม: จัดโครงสร้าง 3, ทำความสะอาด 5, ตรวจความผิดปกติ 4, แยกโซน 1, วัดผลหลังโหลด 8 กับชุดประเมิน 6 stage ไม่มีงานให้ทำ (ไม่มีวันที่ที่ต้องแปลง, ไม่มีกฎจัดหมวดหมู่, schema ไม่เปลี่ยน, ไม่มีกฎจาก Decision Tree, ไม่มีคอลัมน์มูลค่าเงินให้ COPDQ รวม) stage เหล่านี้มี unit test ของตัวเองและทำงานเมื่อข้อมูลมีลักษณะนั้น

**11. ทำไมไม่ใช้ Airflow**
งานมีขั้นตอนเดียวต่อการนำเข้า (ไฟล์เข้า → Spark รัน) จึงใช้ daemon เบาๆ ที่มีคิวต่อตารางและ run registry ส่วนงานตั้งเวลาใช้ n8n ถ้ามีงานที่ต้องพึ่งกันหลายขั้นควรย้ายไป Airflow

## ง. การแปลงข้อมูลและความแม่นยำ (เกณฑ์ 10 คะแนน)

**12. Precision 95.89% หมายความว่าอะไร 30 แถวที่ผิดคืออะไร**
ระบบกักกัน 730 แถว เป็นแถวผิดจริง 700 แถว อีก 30 แถวเป็นข้อมูลถูกต้องที่ถูกกักกัน ทั้ง 30 มาจาก Z-score: 21 แถวคือนักศึกษาที่ได้คะแนน 37–49 (ต่ำกว่าค่าเฉลี่ยเกิน 3σ) และ 9 แถวคือคนที่เรียน 11–12 ชั่วโมง
*พูดเอง:* นี่คือข้อจำกัดที่สำคัญ คะแนนต่ำไม่ใช่ข้อมูลผิด ผลคือรายชื่อนักศึกษาที่ต้องติดตามเหลือ 5 จาก 28 คน ทางแก้: คอลัมน์ที่มีขอบเขตชัดเจน (คะแนน 0–100) ควรใช้กฎช่วงค่าอย่างเดียว ไม่ใช้ Z-score หรือส่งเข้าคิวรอคนตรวจแบบที่เอนจินโต้ตอบทำ ตอนนี้เกณฑ์ 3σ เขียนตายตัวในโค้ด ยังตั้งรายคอลัมน์ไม่ได้

**13. คะแนนที่ว่างถูกจัดการอย่างไร ทำไมเหตุผลเขียนว่า `score=0.0`**
กฎของตารางนี้เติม 0 ให้ค่าว่างก่อน แล้ว IQR จับ 0 เป็นค่านอกช่วง [32, 123] จึงกักกันครบ 300 แถว แต่เหตุผลที่บันทึกไม่ได้บอกว่า "ค่าว่าง"
*พูดเอง:* วิธีนี้ได้ผลกับชุดนี้เพราะ 0 อยู่นอกช่วง ถ้าคะแนนกระจายกว้างกว่านี้ ค่าว่างจะกลายเป็นคะแนน 0 ในข้อมูลสะอาด ที่ถูกคือกักกันค่าว่างของคอลัมน์จำเป็นโดยตรงพร้อมเหตุผล "missing"

**14. ทำไม IQR ใช้ 3.0 ไม่ใช่ 1.5 ตามตำรา**
วัดทั้งสองค่า: 1.5 ได้ false positive 101 แถว (precision 87.39%), 3.0 ได้ 30 แถว (95.89%) โดย recall เท่ากันที่ 100% ค่า 1.5 กักกันนักศึกษาที่เรียน 10–12 ชั่วโมงซึ่งเป็นข้อมูลจริง 3.0 คือ outer fence ของ Tukey เป็นค่าของกรณีทดสอบนี้ ไม่ใช่ค่าที่ถูกสำหรับข้อมูลทุกชนิด และปรับได้ใน `rules_config.json` รายตาราง

**15. แถวซ้ำ 100 แถวหายไปไหน**
`auto_clean` ตัดแถวที่คีย์ `student_id + course + semester` ซ้ำก่อนนับ ไฟล์ 10,100 แถวจึงเหลือ 10,000 แล้วแบ่งเป็น 9,370 + 630
*พูดเอง:* แถวที่ถูกตัดไม่ได้เก็บใน quarantine จึงตรวจย้อนหลังรายแถวไม่ได้ ควรเก็บพร้อมเหตุผล "duplicate"

**16. ทำไมเอนจินสองตัวให้ผลไม่เท่ากัน (9,400 กับ 9,370)**
เอนจินโต้ตอบใช้กฎ 5 ข้อที่ตั้งตามบริบทผู้ใช้ และส่ง outlier เข้าคิวรอคนตรวจ ส่วน Spark ใช้ Z-score เพิ่มอีกชั้นและมีแค่สองโซน ส่วนต่าง 30 แถวคือ false positive จาก Z-score ทั้งหมด

**17. ทดสอบกับข้อมูลจริงที่ไม่รู้คำตอบแล้วเป็นอย่างไร**
รันได้และได้คะแนนคุณภาพ/เหตุผลกักกัน (เช่น churn 440,833 แถว) แต่ไม่มี ground truth จึงวัด precision/recall ไม่ได้ นี่คือขอบเขตของการประเมิน: ความแม่นยำพิสูจน์กับชุดสังเคราะห์ชุดเดียว

**18. รู้ได้อย่างไรว่า refactor แล้วผลไม่เปลี่ยน**
Golden test: รันชุดเดิมก่อนและหลังแยก stage แล้วเทียบจำนวนรวม จำนวนสะอาด จำนวนกักกัน และ breakdown ต้องตรงกันทุกตัว (`c-golden-before.json`, `c-golden-after.json`)

## จ. การสกัดและการโหลด (เกณฑ์ 10 + 5 คะแนน)

**19. อัปโหลดไฟล์เดิมซ้ำ หรืออัปโหลดสองไฟล์พร้อมกัน เกิดอะไร**
ไฟล์ซ้ำ: ตรวจ checksum แล้วตอบ `duplicate` พร้อม `ingest_id` เดิม ไม่รันซ้ำ สองไฟล์พร้อมกัน: ได้ `ingest_id` คนละตัว เข้าคิวของตาราง รันทีละรอบ ไม่ทับกัน หลักฐาน `b-e2e-ingest-check.txt` (PASS 3 ข้อ)

**20. ถ้า Spark ล่มกลางรอบ ข้อมูลเสียหายไหม**
ลำดับการเขียนคือ quarantine ก่อน (ลบของ `ingest_id` เดิมแล้วเขียนใหม่) แล้ว MERGE active ตามคีย์ ทั้งสองขั้นรันซ้ำได้ไม่เกิดแถวซ้อน ไฟล์ดิบย้ายไป archive เมื่อสำเร็จเท่านั้น ทดสอบหยุด worker กลางรอบ: สถานะค้าง RUNNING แล้วรันต่อเองจน SUCCEEDED เมื่อ worker กลับมา (T14.1)
*ระวัง:* quarantine กับ active ไม่ได้อยู่ใน transaction เดียวกัน ที่รับประกันคือ "รันซ้ำแล้วถูก" ไม่ใช่ "atomic"

**21. ป้องกัน SSRF / SQL injection ตอนนำเข้าอย่างไร**
URL: allowlist แบบ fail-closed (รับเฉพาะ data.go.th และ host ที่ตั้งใน `.env`) และตรวจซ้ำทุก redirect hop จึงเด้งไปบริการภายในไม่ได้ ทดสอบ 5 URL ได้ 400 ทั้งหมด (T3.1) SQL: รับเฉพาะคำสั่งเดียวที่ขึ้นต้นด้วย SELECT, session แบบ read-only, statement timeout, เพดานจำนวนแถว (T4.3) โค้ดอยู่ที่ `services/api/app/api/ingest_guards.py`

**22. เวลาประมวลผลเป็นอย่างไรเมื่อข้อมูลโตขึ้น**
10K 66 วิ, 100K 85 วิ, 500K 203 วิ, 1M 414 วิ (ในเอนจิน) ข้อมูล 100 เท่าใช้เวลาเพิ่ม 6.3 เท่า เพราะราว 60 วิแรกเป็นต้นทุนเริ่ม Spark คอขวดที่ 1M คือ `quarantine_assembly` 146 วิ ผ่านข้อกำหนด TOR (ล้านแถวไม่เกิน 10 นาที)
*ต้องทำ Task 1 ก่อน:* ไม่อย่างนั้นตารางในรายงานจะขึ้น FAILED

**23. ทำไมเลือกคีย์หลักผิดได้ (บั๊ก 1,030 → 250 แถว)**
เดิมเดาคีย์จากชื่อคอลัมน์ (`student_id`) ทั้งที่คีย์จริงเป็นคีย์ผสม MERGE จึงทับกัน แก้แล้วให้เดาจากข้อมูล (หาชุดคอลัมน์ที่เล็กที่สุดที่ไม่ซ้ำ) และมี unit test ทางที่ปลอดภัยที่สุดคือลงทะเบียนคีย์ใน schema registry
*ใช้เป็นตัวอย่างว่าการทดสอบการใช้งานจริงเจอบั๊กที่ unit test ไม่เจอ*

## ฉ. การใช้ประโยชน์ (เกณฑ์ 5 คะแนน)

**24. ข้อมูลที่สะอาดแล้วเอาไปทำอะไรได้ ดีกว่าข้อมูลดิบแค่ไหน**
เปิดตารางเทียบสามชุดใน `docs/evaluation/d-utilization.md` (มีหลังทำ Task 3): ข้อมูลดิบให้อัตราผ่าน 98.94% และมีคะแนน −10 ถึง 150 ปนอยู่, ข้อมูลอ้างอิง 99.72%, หลัง ETL 99.95% ค่าเฉลี่ยรายวิชาหลัง ETL ห่างจากค่าจริงไม่เกิน 0.1 คะแนน
*พูดเอง:* รายชื่อนักศึกษาที่ต้องติดตามพบ 5 จาก 28 คน (ดูข้อ 12)

**25. Dashboard แสดงอะไร เชื่อได้แค่ไหน**
KPI รวม (จำนวนแถว คะแนนเฉลี่ย จำนวนกักกัน) ตรงกับ aggregation ใน Elasticsearch ทุกค่า (T10.1) จุดที่ยังผิด: สัดส่วน missing/duplicate/invalid ขึ้น 0%, ตัวกรอง Time กับ Business Area ไม่มีผล — ไม่ควรสาธิตสองจุดนี้ และถ้าถูกถามให้ยอมรับว่าเป็นบั๊กที่รู้แล้ว (F-22, F-23)

**26. Trust-Check API ใช้อย่างไร**
ระบบปลายทางเรียก `GET /api/v1/lineage/{table}/trust-check` ก่อนอ่านข้อมูล ได้ `is_safe_to_consume` จากคะแนนล่าสุดเทียบเกณฑ์ของตาราง และจำนวนคำขอ schema ที่ค้าง ถ้ามี schema drift ค้างจะตอบ `HALT_INGEST` (T8.1)

## ช. นวัตกรรม (เกณฑ์ 15 คะแนน)

**27. นวัตกรรมของงานนี้คืออะไร**
สามเรื่องที่ชี้โค้ดได้: (1) เหตุผลรายแถวและเอนจินโต้ตอบที่อธิบายที่มาของกฎทุกข้อ (2) เกณฑ์ที่ปรับตามประวัติและการตรวจการกระจายเปลี่ยนด้วย PSI (3) ประตูอนุมัติ: schema drift และกฎที่ AI เสนอ ต้องผ่านคนก่อนมีผล
*พูดเอง:* ยังไม่ได้วัดแยกว่าแต่ละตัวช่วยได้กี่เปอร์เซ็นต์

**28. AI ทำอะไรในระบบ ถ้าไม่มี AI ระบบทำงานไหม**
สองจุด: อธิบายบริบทของกฎในเอนจินโต้ตอบ (Groq, ทดสอบแล้วว่าเรียกจริง T11.5) และเสนอกฎใหม่เมื่อพบความผิดปกติ ซึ่งต้องมีคนอนุมัติ การตรวจคุณภาพหลักเป็นกฎและสถิติ ไม่พึ่ง AI ปิด AI ได้ด้วย compose profile
*ระวัง:* ปุ่ม "วิเคราะห์ด้วย AI" ในหน้า Rules ใช้แถวกักกันจริงและเรียก Groq (สำรอง Ollama แล้วกฎคงที่) ป้ายบนข้อเสนอบอกว่าใช้เอนจินไหน ถ้าไม่มีแถวกักกันจะตอบ 404 ไม่แต่งข้อเสนอ ส่วนรายการตัวอย่างสามรายการที่ขึ้นเมื่อยังไม่มีข้อเสนอจริงมีป้าย "ตัวอย่าง" และการอนุมัติไม่เปลี่ยนกฎ อย่าบอกว่าเป็นผลจาก LLM ส่งแถวกักกันไปให้ Groq โดยปิดค่าคอลัมน์ระบุตัวตน แต่ค่าอื่นยังออกนอกเครื่อง ถ้าต้องไม่ให้ข้อมูลออกเลยให้ปิด Groq แล้วใช้ Ollama

**29. COPDQ คิดอย่างไร ตัวเลขเชื่อได้ไหม**
สามส่วน: ค่าแก้ไข = แถวที่กักกัน × $2 · โอกาสที่เสีย = ผลรวมคอลัมน์มูลค่าเงิน (เช่น `total_sales`, `amount`) ของแถวที่กักกัน ถ้าตารางไม่มีคอลัมน์เงินใช้ แถว × 5% × $50 · ความเสี่ยง = แถว × ระดับ schema drift เป็นการประมาณเพื่อจัดลำดับความสำคัญ ค่าคงที่ $2 / $50 / 5% เป็นค่าสมมติ ไม่ใช่ตัวเลขการเงินจริง (รายละเอียด `docs/whitebox-report/07-copdq-financial-impact.md`)

**30. พยากรณ์คุณภาพ 7 วันทำอย่างไร**
OLS linear regression บนคะแนนคุณภาพตามเวลา พร้อมช่วงความเชื่อมั่นจาก standard error (`docs/whitebox-report/06-quality-forecast.md`) จุดข้อมูลมีน้อยและไม่ได้วัดความแม่นยำของการพยากรณ์
*ระวัง:* TOR ข้อ 3.2 เขียนว่าใช้ sine wave ร่วมด้วย ส่วนวัตถุประสงค์เขียน OLS ถ้าถูกถามให้ตอบตามโค้ดปัจจุบัน

## ซ. คุณภาพงานและการทดสอบ

**31. ทดสอบระบบอย่างไร**
สามชั้น: (1) unit test: API 156, UI 76, สคริปต์ 39, Spark 60 (2) golden test และวัดกับ ground truth (3) ทดสอบการใช้งานจริง 88 ข้อ ครอบคลุม API ทุกเส้น ผ่าน 66 ไม่ผ่าน 18 ข้าม 4 บั๊กระดับสูง 6 ตัวแก้แล้วทั้งหมด
*จุดแข็งที่ควรเน้น:* รายงานบันทึกข้อที่ไม่ผ่านตามจริง ไม่แก้ผลคาดหวังให้ตรงผลที่ได้

**32. บั๊กที่ยังเหลือมีอะไร**
ระดับกลาง: lineage inspect คืนค่าประมาณ (F-13), ปุ่มเชื่อมต่อ DB/API/Stream เป็นโหมดสาธิต (F-19), Dashboard breakdown และตัวกรอง (F-22, F-23), ปุ่ม Generate (F-6) ระดับต่ำอีก 7 ข้อ รายการเต็มอยู่ในรายงานทดสอบ

**33. ใช้ AI ช่วยเขียนโค้ดไหม เข้าใจโค้ดแค่ไหน**
ตอบตามจริง ถ้าใช้ให้บอกว่าใช้กับส่วนไหน และพิสูจน์ความเข้าใจด้วยการเปิด stage หนึ่งตัวแล้วอธิบายทีละบรรทัด แนะนำ `services/spark/sdoqap/stages/anomaly.py` ฟังก์ชัน `anomaly_iqr` (40 บรรทัด): อ่านกฎ → หาคอลัมน์ตัวเลข → คำนวณช่วง IQR → แยกแถวนอกช่วงพร้อมเหตุผล → ที่เหลือเป็น `clean_df`

**34. ถ้ามีเวลาอีก 1 เดือนจะทำอะไร**
(1) ให้เกณฑ์ Z-score ตั้งรายคอลัมน์ได้ และเพิ่มโซนรอคนตรวจในเส้นทาง Spark (2) เก็บแถวซ้ำและค่าว่างลง quarantine พร้อมเหตุผลตรงตัว (3) วัดความแม่นยำกับชุดข้อมูลจริงที่ติดป้ายด้วยมือ (4) บันทึกจำนวนแถวเข้า/ออกราย stage (5) วัด MTTD และผลของฟีเจอร์นวัตกรรมแยกรายตัว
