## Slide 1 — "ข้อมูลของเรามาจากไหน?"

**Key Message:** ข้อมูลจริงไม่ได้มาจากที่เดียวหรือหน้าตาเดียว — ระบบต้องรับได้หลายแบบ และต้องรู้ว่าแต่ละแบบเสี่ยงอะไร

**เนื้อหาบนสไลด์**
- หัวใหญ่: **ข้อมูลของเรามาจากไหน?** · รองหัว: *ข้อมูลกระจายอยู่ในหลายรูปแบบและหลายระบบ*
- 4 การ์ด (เลข 01–04) ตามที่ระบบรับเข้าได้จริง:
  - **01 ไฟล์ CSV / Excel** 🟢 — อัปโหลดผ่านหน้าเว็บ (Excel อ่าน sheet แรก)
  - **02 REST API** 🟢 — ดึง JSON/CSV จาก URL (มีตัวช่วยสำหรับ data.go.th)
  - **03 ฐานข้อมูล PostgreSQL** 🟢 — เขียน SELECT ดึงแบบอ่านอย่างเดียว
  - **04 Stream (Reddit → Kafka)** 🟡 — มีจริงแต่เป็นอีกเส้นทางหนึ่ง ยังไม่ผ่านการตรวจคุณภาพ
- แถบสรุปล่าง: **"ต่างแหล่ง ต่างรูปแบบ ต่างความเสี่ยง — ท่อข้อมูลจึงต้องจัดการได้ยืดหยุ่น"**
- ข้อมูลทดสอบที่ใช้ในระบบนี้ (ติดป้ายเล็ก): ชุดคะแนนนักเรียน 10,100 แถว (ใส่ข้อผิดพลาดไว้ล่วงหน้า), ไฟล์ขนาด 10K–1M แถวใน repo

**Diagram ที่ควรวาด** (สไตล์เดียวกับหน้า 7 ของไฟล์อ้างอิง: การ์ดซ้อนแนวตั้ง ไอคอนซ้าย คำอธิบายขวา)
```
[CSV/Excel] ─┐
[REST API ] ─┼─►  ท่อข้อมูล SDOQAP  ─►  ?
[PostgreSQL] ┤
[Reddit stream] ┄┄► (อีกเส้น)
```
การ์ดที่ 4 ใช้เส้นประและป้ายสีเหลือง "ยังไม่เชื่อมระบบตรวจคุณภาพ"

**สิ่งที่ผู้พูดควรพูด (≈45 วินาที)**
"ก่อนจะพูดถึงท่อข้อมูล ต้องเริ่มจากคำถามว่าข้อมูลมาจากไหน ในระบบของเรา ข้อมูลมาได้ 4 ทาง ไฟล์ CSV หรือ Excel ที่ผู้ใช้อัปโหลด เว็บเซอร์วิส REST API ฐานข้อมูล PostgreSQL และสตรีมจาก Reddit สามทางแรกต่อเข้าท่อตรวจคุณภาพของเราครบ ส่วน Reddit เป็นเส้นทางแยกที่ยังไม่ผ่านการตรวจ แต่ละทางมีความเสี่ยงต่างกัน ไฟล์อาจเข้ารหัสผิด API อาจมีข้อมูลซ้อนกัน ฐานข้อมูลอาจใหญ่เกินไป ดังนั้นเราต้องมีท่อที่จัดการได้ยืดหยุ่น"

**Technical evidence จากโค้ด**
- ไฟล์: `API/pipeline.py:315-333` (`ingest_csv`; Excel → CSV ที่ `:324-329`)
- REST: `pipeline.py:335-508` (`ingest_api`; resolver data.go.th `:354-435`)
- PostgreSQL: `pipeline.py:567-613` (`ingest_rdbms`; `db_type` ต้องเป็น `postgresql`)
- Stream: `streaming_job.py` + `reddit_stream.py` → Parquet `/data/reddit/parquet` และ ES `reddit`; ไม่มีการอ้างถึงใน `spark_quality_engine.py` (ยืนยันด้วย grep `reddit` ใน engine ไม่พบ)
- **ข้อควรระวัง:** แท็บ "API" และ "Stream" บนหน้า Ingestion เป็นโหมดสาธิต (`whitebox.py:1593-1618` ตอบ `"simulated": True`) — ถ้าจะสาธิตการดึงจาก API ให้ใช้เรียก API ตรงหรือผ่าน n8n ไม่ใช่กดแท็บนั้น
- ไม่รองรับ: ไฟล์ JSON/Parquet/Avro/XML, ฐานข้อมูลอื่นนอกจาก PostgreSQL 🔴

**ประโยคจำ:** ความหลากหลายของแหล่งข้อมูลคือเหตุผลที่ต้องมีท่อข้อมูล
**ประโยคเชื่อม:** "แล้วทำไมแค่ดึงข้อมูลมาเก็บไว้ถึงไม่พอ?"

**ครอบคลุมเกณฑ์:** ข้อ 3 (ส่วนแหล่งข้อมูลที่รองรับ) · เป็นบริบทให้ข้อ 2

## Slide 2 — "ทำไมต้องมี Data Pipeline หลายกระบวนการ?" *(พื้นมืด — จุดเปลี่ยนเข้าสู่ท่อ)*

**Key Message:** ข้อมูลดิบมีปัญหาหลายชั้น แต่ละชั้นต้องการกระบวนการเฉพาะ — ระบบจึงมี 21 ขั้นใน 3 ช่วง จัดเป็น 6 กลุ่ม

**เนื้อหาบนสไลด์** (ใช้โครงเดียวกับหน้า 3 ของไฟล์อ้างอิง: 4 ปัญหาเป็นแถวเลข 01–04 พร้อมคำตอบ)

| # | เมื่อข้อมูลดิบมาแบบนี้… | ระบบตอบด้วยกระบวนการ… |
|---|---|---|
| 01 | **โครงสร้างไม่ตรงกัน** — ชื่อ/ชนิดคอลัมน์ต่างจากที่คาด | จัดโครงสร้าง (ALIGN) + ตรวจการเปลี่ยนแปลง schema (schema drift) |
| 02 | **ค่าผิด ว่าง หรือซ้ำ** | ล้างข้อมูล · ตรวจกฎ · ลบซ้ำ |
| 03 | **รูปแบบไม่เหมือนกัน** — เช่น วันที่หลายแบบ รวมปี พ.ศ. | มาตรฐานค่า (standardize) |
| 04 | **ค่าผิดปกติที่ไม่ได้ผิดกฎตรง ๆ** | ตรวจด้วยสถิติ (IQR / Z-score) แล้วแยกเข้ากักกัน |
| 05 | **ข้อมูลเสียไม่ควรปนกับข้อมูลดี** | แยก Valid / Invalid → Quarantine |
| 06 | **ต้องรู้ว่าผลเป็นอย่างไร** | วัดผลหลังโหลด (คะแนนคุณภาพ, ความสดใหม่ ฯลฯ) |

- แถบ **21 = 1 + 12 + 8** (ALIGN 1 · TRANSFORM 12 · POST-LOAD 8) พร้อมสัญลักษณ์ "+ ขั้นตอนภายในอีก 7 + กระบวนการฝั่ง API อีกอย่างน้อย 10"
- แถบสรุปล่าง: **"ทุกขั้นรันอัตโนมัติ หลังผู้ใช้ส่งข้อมูลเข้าระบบ"**

**Diagram ที่ควรวาด** — แถบ 6 ช่องต่อกัน (แนวนอน) ตัวเลขใต้ช่องคือจำนวน stage
```
ALIGN → ล้าง/ตรวจ → มาตรฐานค่า → ตรวจผิดปกติ → แยกกักกัน → [โหลด] → วัดผลหลังโหลด
  1        4              2            4             2                     8
```
ช่อง [โหลด] วาดเส้นประ (เป็นขั้นตอนภายใน ไม่ใช่ stage ที่ลงทะเบียน)

**สิ่งที่ผู้พูดควรพูด (≈55 วินาที)**
"ถ้าข้อมูลสะอาดอยู่แล้ว เราคงไม่ต้องมีท่อ แต่ข้อมูลจริงมีปัญหาหลายชั้น โครงสร้างไม่ตรง ค่าผิด ค่าว่าง ซ้ำ รูปแบบไม่เหมือนกัน และมีค่าที่ผิดปกติแบบที่กฎตรง ๆ จับไม่ได้ แต่ละปัญหาต้องใช้กระบวนการต่างกัน ระบบเราจึงแบ่งเป็น 21 ขั้น ใน 3 ช่วง คือจัดโครงสร้าง 1 ขั้น แปลงและตรวจ 12 ขั้น และวัดผลหลังโหลด 8 ขั้น เพื่อให้เห็นภาพ ผมจัดเป็น 6 กลุ่ม นอกจากนี้ยังมีขั้นตอนที่อยู่ในโค้ดอีก เช่น การล็อกตารางและการ MERGE และกระบวนการฝั่ง API เช่น ตรวจไฟล์ซ้ำ ทั้งหมดทำงานอัตโนมัติ"

**Technical evidence จากโค้ด**
- รายชื่อ 3 ช่วง: `S/pipeline/plan.py:2-6`; ลงทะเบียนและจับเวลาต่อ stage: `registry.py:17-32` (`stage_seconds`)
- ลำดับจริงของงานหนึ่งรอบ: `SQE:run_quality_check` (`spark_quality_engine.py:1551-1811`)
- ขั้นตอนภายใน 7: ขอ lock · อ่าน raw · เขียน quarantine · MERGE active · OPTIMIZE/VACUUM · trigger Gold · archive raw
- คิวงาน 1 งาน/ตาราง: `trigger_core.py:53-82`; lock ใน ES พร้อม heartbeat: `SQE:126-218`
- **ที่ต้องบอกถ้าถูกถาม:** `standardize_categories` ต้องมี `standardization_rules` ใน registry ซึ่งไม่พบตัวเขียนค่านี้ใน repo (ผลน้อย) 🟡; `anomaly_induced` มักว่าง (ต้องมีกฎที่คนอนุมัติ) 🟡

**ประโยคจำ:** หนึ่งปัญหา หนึ่งกระบวนการ — ยิ่งข้อมูลดิบ ยิ่งต้องมีหลายด่าน
**ประโยคเชื่อม:** "ด่านแรกสุดคือก่อนข้อมูลจะเข้าระบบ — ระบบตรวจอะไรบ้าง?"

## Slide 3 — "ก่อนรับข้อมูลเข้าระบบ เราตรวจอะไร?"

**Key Message:** ด่านแรกกันของเสียและของอันตรายตั้งแต่ประตู แล้วเก็บสำเนาดิบพร้อมบันทึกประวัติ ทุกครั้งที่นำเข้า

**เนื้อหาบนสไลด์**
- 7 การ์ด (ตรวจที่ API ก่อนลงไฟล์) ทั้งหมด 🟢:
  - **01 ยืนยันตัวตน** (session หรือ service key)
  - **02 ชื่อตาราง** — อนุญาตเฉพาะตัวอักษร ตัวเลข `_` `-` (กันการแอบอ้างเส้นทางไฟล์)
  - **03 ขนาดไฟล์** — ไม่เกิน 200 MB
  - **04 ไฟล์ว่าง** — ปฏิเสธทันที
  - **05 ไฟล์ซ้ำ** — คำนวณ SHA-256 ถ้าเคยรับแล้วจะไม่รับซ้ำ
  - **06 คอลัมน์คีย์หลัก** — ถ้าตารางมีคีย์ลงทะเบียนไว้ ไฟล์ต้องมีคอลัมน์นั้น
  - **07 ป้องกัน URL/SQL อันตราย** — REST: อนุญาตเฉพาะ host ที่กำหนด · ฐานข้อมูล: SELECT เท่านั้น, อ่านอย่างเดียว, timeout 30 วินาที, ไม่เกิน 1,000,000 แถว
- ช่องล่าง "แล้วหลังผ่านด่าน": แปลงทุกแหล่งเป็น CSV → เก็บ **ไฟล์ดิบ 1 โฟลเดอร์ต่อ 1 การนำเข้า** ใน HDFS → บันทึก run (สถานะ QUEUED) → สั่ง Spark
- กล่อง "สิ่งที่ยังไม่มี" (พูดเอง ไม่รอถูกถาม): 🔴 ไม่เทียบจำนวนแถวต้นทางกับที่รับเข้า · 🔴 ไม่ตรวจ encoding/delimiter · 🟡 REST ฝั่ง API ไม่มี pagination/retry
- แถบสรุปล่าง: **"รับเข้าอย่างมีบันทึก — รู้ว่าอะไรเข้ามา เมื่อไร และมาจากไหน"**

**Diagram ที่ควรวาด**
```
ผู้ใช้/n8n ─► [ด่านตรวจ 7 ข้อ] ─► แปลงเป็น CSV ─► HDFS /raw/<ตาราง>/<ingest_id>/ ─► บันทึก run ─► Spark
                    │ ไม่ผ่าน
                    ▼
              ตอบกลับ 400/413 (ไม่ลงไฟล์)
```
ใต้ "บันทึก run" วาดการ์ดเล็กแสดงสถานะ: QUEUED → RUNNING → SUCCEEDED / FAILED / SKIPPED / TRIGGER_FAILED

**สิ่งที่ผู้พูดควรพูด (≈55 วินาที)**

## Slide 4 — "ข้อมูลต่างรูปแบบ ทำให้ใช้ร่วมกันได้อย่างไร?"

## Slide 5 — "เราตรวจคุณภาพข้อมูลอย่างไร?"

**Key Message:** ตรวจ 3 ชั้น — กฎตรง ๆ, สถิติ, และการเฝ้าดูแนวโน้ม — และทุกแถวที่ไม่ผ่านมี "เหตุผลระบุได้"

**เนื้อหาบนสไลด์**
- **ชั้นที่ 1 กฎตรง ๆ (ทุกข้อ → เหตุผลบันทึกต่อแถว)** 🟢
  - คีย์หลักว่าง → `missing_primary_key`
  - ค่าว่างในคอลัมน์ → `null_value_in_<คอลัมน์>`
  - ชนิดไม่ถูกต้อง → `invalid_type_<คอลัมน์>`
  - วันที่ว่าง → `missing_date`
  - คีย์หลักซ้ำ → `duplicate_records`
  - เกินช่วงที่ตั้ง → `out_of_range_<คอลัมน์>` (ต้องตั้ง `range_checks`)
- **ชั้นที่ 2 สถิติ** 🟢 — IQR (ค่าเริ่มต้นตัวคูณ 1.5) และ Z-score เกิน 3.0 → ตรวจทุกคอลัมน์ตัวเลข
- **ชั้นที่ 3 เฝ้าแนวโน้ม** 🟡 — คะแนนต่ำกว่าเกณฑ์ → alert; อัตราแถวกักกันผิดปกติเทียบประวัติ (ต้องมี ≥ 3 รอบ) → alert; profile drift (PSI) เมื่อเปิด AI advisor
- **สูตรคะแนน:** `Quality Score = Clean ÷ (Clean + Quarantine) × 100`
- ตัวอย่างเหตุผลจริง (กล่องเล็ก) ชุดคะแนนนักเรียน 10,100 แถว ที่ใส่ข้อผิดพลาดล่วงหน้า: คะแนนว่าง 300 · คะแนนเกินช่วง 200 · ค่าผิดปกติ 100 · แถวซ้ำ 100 (ตามไฟล์ `ground_truth.csv` และ README ของชุดข้อมูล — ตัวเลขนี้เป็นเฉลยที่ฝังไว้ ไม่ใช่ผลการรัน)
- มิติที่วัดจริง: ความครบ (Completeness) · ความไม่ซ้ำ (Uniqueness) · ความถูกต้องตามกฎ (Validity) 🟢 · ความสดใหม่ (Timeliness) 🟡 วัดแต่ไม่เทียบเกณฑ์ · ความสอดคล้อง/ความแม่นยำ 🔴 ในเส้นหลักยังไม่มี
- แถบสรุปล่าง: **"ไม่มีแถวไหนถูกปฏิเสธโดยไม่บอกเหตุผล"**

**Diagram ที่ควรวาด** — พีระมิด/บันได 3 ชั้น (กฎ → สถิติ → แนวโน้ม) ข้างขวามีกล่องสูตรคะแนน และตัวอย่างตาราง quarantine (คอลัมน์: ข้อมูลเดิม | `reject_reason`)

**สิ่งที่ผู้พูดควรพูด (≈55 วินาที)**
"เราตรวจคุณภาพ 3 ชั้น ชั้นแรกคือกฎตรง ๆ เช่น คีย์หลักห้ามว่าง ห้ามมีค่าว่าง ชนิดต้องถูก ห้ามซ้ำ ชั้นที่สองใช้สถิติ IQR และ Z-score จับค่าที่ผิดปกติแม้จะไม่ผิดกฎตรง ๆ ชั้นที่สามเฝ้าดูแนวโน้ม ถ้าคะแนนตกหรืออัตราแถวเสียพุ่งผิดปกติ ระบบแจ้งเตือน ทุกแถวที่ไม่ผ่านจะมีเหตุผลกำกับ คะแนนคุณภาพคือสัดส่วนแถวที่ผ่านต่อแถวทั้งหมด ข้อควรรู้คือมิติความสอดคล้องและความแม่นยำยังไม่มีในเส้นหลัก และบางสวิตช์ในไฟล์ตั้งค่า เช่น ปิดการตรวจคีย์ว่าง ยังไม่ถูกอ่านโดยระบบ"

## Slide 6 — "ข้อมูลผ่าน / ไม่ผ่าน จัดการอย่างไร?"

**Key Message:** ระบบ **แยก** ข้อมูลที่ไม่ผ่านออกก่อนโหลด (ไม่ทิ้ง) ส่วน **คะแนนคุณภาพ** คิดหลังโหลดเพื่อแจ้งเตือนและควบคุมขั้นต่อไป ไม่ได้หยุดการโหลด

**เนื้อหาบนสไลด์**
- **สองด่านที่ต้องแยกให้ชัด** (ใช้การเทียบสองฝั่งแบบหน้า 4 ของไฟล์อ้างอิง):

| ด่านที่ 1 · แยกรายแถว (ก่อนโหลด) 🟢 | ด่านที่ 2 · คะแนนคุณภาพ (หลังโหลด) |
|---|---|
| แถวผ่าน → ไปตาราง **Active** | คำนวณหลังเขียน Delta แล้ว |
| แถวไม่ผ่าน → ไปตาราง **Quarantine** พร้อมเหตุผล | ใช้ส่ง alert · ติดสถานะ `warnings` · ตัดสินว่าจะสร้างตารางสรุป Gold หรือไม่ |
| ไม่ลบทิ้ง | **ไม่หยุดการโหลด** (🔴 ไม่มี gate ระดับตารางก่อนโหลด) |

- **เกณฑ์ (threshold):** ค่าเริ่มต้น 90 พื้น 70 · โหมด adaptive = เฉลี่ย 15 รอบล่าสุดลบส่วนเบี่ยงเบน แต่ไม่ต่ำกว่าพื้น
- **ผู้ใช้ปลายทางถามได้ว่า "ตารางนี้ใช้ได้ไหม":** Trust-check → `SAFE` / `WARNING_SUSPECT` / `HALT_INGEST` 🟢 (คำแนะนำ ผู้เรียกเลือกใช้เอง)
- **หลังกักกัน:** มีทางไปต่อ 2 ทาง → (ก) AI เสนอกฎ ให้คนอนุมัติ (ข) ระบบแก้อัตโนมัติรอบเดียว (ดู Slide 9)
- แถบสรุปล่าง: **"ข้อมูลเสียไม่ปนกับข้อมูลดี และไม่หายไปไหน"**

**Diagram ที่ควรวาด**
```
แปลง+ตรวจ ──┬─ ผ่าน ───► Delta Active   ─┐
            └─ ไม่ผ่าน ─► Delta Quarantine ─┤  (เขียนก่อน)
                                          ▼
                              คิดคะแนนหลังโหลด ─► alert / state / Gold
                                          │
```

## Slide 9 — "AI / LLM ช่วยตรงไหน?" *(พื้นมืด — อิงรูปแบบหน้า 5–6 ของไฟล์อ้างอิง)*

**Key Message:** AI ในระบบนี้ช่วย 4 งานที่เจาะจง — ส่วนตรวจคุณภาพ แปลง และคำนวณตัวเลข เป็นกฎและสถิติที่ตรวจสอบได้ ไม่ใช่ AI

**เนื้อหาบนสไลด์**
- **การ์ดเลข 01–04: AI ช่วยตรงนี้จริง**
  - **01 ออกแบบแดชบอร์ด** 🟢 — LLM (Groq) สร้างโครง (spec) จากความต้องการ + สถิติคอลัมน์; ระบบตรวจก่อนใช้ ถ้า LLM ใช้ไม่ได้ → โหมดกฎอัตโนมัติ
  - **02 เสนอกฎคุณภาพ** 🟢 — AI advisor วิเคราะห์ตัวอย่างแถวที่ถูกกัก (≤ 20 แถว ปิดคอลัมน์ที่เป็นรหัสประจำตัว) → เป็น "ข้อเสนอ" ต้องมีคนอนุมัติ
  - **03 สร้างกฎแก้ไขอัตโนมัติ** 🟡 — เมื่อมีแถวถูกกัก ระบบให้ LLM สร้างกฎแก้ แล้ว **ใช้อัตโนมัติถ้าความมั่นใจ ≥ 0.80** และรันซ้ำหนึ่งรอบ (ไม่ต้องมีคนอนุมัติ)
  - **04 เรียบเรียงข้อความสรุปบนหน้า Dashboard** 🟡 — ใช้ข้อเท็จจริงที่คำนวณไว้แล้ว ไม่คิดตัวเลขใหม่
- **ตารางเทียบกับ 5 จุดที่ไฟล์อ้างอิงให้ AI ช่วย** (พูดตรง ๆ ว่าอะไรคือ AI อะไรไม่ใช่):

| จุดที่ AI ETL ทั่วไปกล่าวถึง | SDOQAP ทำอย่างไรจริง |
|---|---|
| Intelligent Schema Mapping | **ไม่ใช่ AI** — จัดชื่อด้วยอัลกอริทึม (`normalize_name`) + ตรวจ drift แล้วให้คนอนุมัติ 🟡 |
| Dynamic Transformation | กฎ DSL (`fillna/calculate/cast/filter/standardize`) — ตั้งโดยผู้ใช้ หรือ LLM สร้างในโหมดแก้อัตโนมัติ 🟡 |
| Automated Anomaly Detection | **สถิติ + ML ไม่ใช่ LLM** — IQR, Z-score 3.0, และ decision tree (Spark ML) เรียนรู้กฎจากแถวที่ผ่าน/ไม่ผ่าน (ต้องมีคนอนุมัติ) 🟢 |

## Slide 10 — "ภาพรวมทั้งระบบ ตั้งแต่ต้นจนจบ"

**Key Message:** SDOQAP ไม่ได้ทำแค่ ETL แต่รวมการตรวจคุณภาพ การกักกัน การติดตาม และการนำข้อมูลไปใช้ ไว้ในวงจรเดียว

**เนื้อหาบนสไลด์** (เรียงลงแนวตั้ง 7 ขั้น แต่ละขั้น 1 ประโยค พร้อมจุดสถานะ)
1. **แหล่งข้อมูล** — ไฟล์ CSV/Excel · REST API · PostgreSQL 🟢 (Reddit stream แยกเส้น 🟡)
2. **รับเข้า** — ตรวจสิทธิ์ ชื่อ ขนาด ไฟล์ว่าง ไฟล์ซ้ำ แล้วเก็บดิบใน HDFS ต่อหนึ่งการนำเข้า 🟢
3. **แปลง** — Spark จัดโครงสร้าง ล้าง ลบซ้ำ มาตรฐานค่า ผ่าน 21 ขั้น 🟢
4. **ตรวจคุณภาพ** — กฎ + สถิติ ระบุเหตุผลทุกแถวที่ไม่ผ่าน 🟢
5. **ผ่าน / กักกัน** — แถวผ่านไป Active, แถวไม่ผ่านไป Quarantine; คะแนนคิดหลังโหลดเพื่อเตือน 🟢
6. **จัดเก็บ** — Delta MERGE ตามคีย์ + ประวัติใน Elasticsearch + archive ไฟล์ดิบ 🟢 (ยังไม่มี rollback/กระทบยอดต้นทาง)
7. **ใช้ประโยชน์** — สร้างแดชบอร์ดด้วย AI · ส่งออก · Trust-check 🟢 (บางส่วนของหน้า Dashboard เป็นข้อมูลจำลอง 🟠)
- แถบปิดท้าย (ตัวใหญ่): **"SDOQAP ไม่ได้ทำแค่ ETL แต่รวม Data Quality, Quarantine, Monitoring และการนำข้อมูลไปใช้ผ่าน Dashboard เข้าด้วยกัน"**
- มุมล่างขวา: เส้นแยก Reddit → Kafka → Spark Streaming → Parquet + ES (ยังไม่เข้าระบบตรวจ)
- ป้าย "Monitoring" 🟡: เก็บเมตริกและส่ง alert ได้ในโค้ด แต่ปลายทางแจ้งเตือน (Slack/LINE) ต้องตั้งค่าเอง, workflow n8n ต้อง import เอง, Grafana มี datasource + alert rules แต่ไม่มี dashboard

**Diagram ที่ควรวาด** — ภาพเดียวแนวนอน 7 กล่อง (ต่อกันด้วยลูกศรหนา เหมือนหน้า 2 ของไฟล์อ้างอิง) แถวล่าง = ที่เก็บ (HDFS · Delta · Elasticsearch) และแถวบน = ผู้กระทำ (API · Spark · LLM · ผู้ใช้)
```

   (ผู้ใช้)     (API)   (Spark)   (Spark)        (Spark)     (Delta+ES)  (ผู้ใช้+LLM+pandas)
```

**สิ่งที่ผู้พูดควรพูด (≈50 วินาที)**
"สรุปภาพรวม ข้อมูลเข้ามาจากไฟล์ API หรือฐานข้อมูล ผ่านด่านตรวจที่ API เก็บดิบใน HDFS แล้ว Spark แปลงและตรวจผ่าน 21 ขั้น แถวที่ผ่านไปตารางใช้งานด้วย MERGE แถวที่ไม่ผ่านไปตารางกักกันพร้อมเหตุผล ประวัติทุกรอบเก็บใน Elasticsearch จากนั้นผู้ใช้ใช้ข้อมูลที่ผ่านแล้วสร้างแดชบอร์ดโดยมี AI ช่วยออกแบบ หรือส่งออกเป็น CSV ข้อจำกัดที่เรารู้และเปิดเผยคือ ยังไม่มี rollback ยังไม่กระทบยอดต้นทางกับปลายทาง คะแนนคุณภาพคิดหลังโหลด และบางส่วนของหน้า Dashboard เป็นข้อมูลจำลอง สรุปคือ SDOQAP ไม่ได้ทำแค่ ETL แต่รวมการตรวจคุณภาพ การกักกัน การติดตาม และการนำข้อมูลไปใช้เข้าด้วยกัน"
