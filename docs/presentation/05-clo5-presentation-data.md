## 3. ความครบถ้วนของ Data Extraction — 10 คะแนน

| หลักฐาน | ผล | ไฟล์ |
|---|---|---|
| PostgreSQL → ระบบ | แถวในตารางต้นทาง 10,100 = แถวที่ ingest ตอบกลับ 10,100 · `SUCCEEDED` · 0.6 MB | `d-rdbms-ingest.json` |
| ไฟล์ 2 ไฟล์ติดกัน ได้ `ingest_id` ต่างกัน | PASS | `b-e2e-ingest-check.txt` |
| ส่งไฟล์เดิมซ้ำ | PASS · ตอบ `status: duplicate` ไม่สร้าง raw ใหม่ | `b-e2e-ingest-check.txt` |
| ประมวลผลครบทั้งสองไฟล์ | PASS · `SUCCEEDED` ทั้งคู่ | `b-e2e-ingest-check.txt` |
| raw ถูก archive ไม่ถูกลบ | พบ 2 โฟลเดอร์ใน `/data/archive/` | `b-e2e-ingest-check.txt` |
| ไฟล์ทดสอบรู้จำนวนแถวแน่นอน | clean 10,000 · dirty 10,100 · ground truth 10,100 | `d-source-inventory.json` |

**กลไกป้องกันข้อมูลหาย/เสีย** (จากโค้ด `services/api/app/api/{pipeline,ingest_guards,run_registry}.py`): `ingest_id` และโฟลเดอร์ raw แยกต่อครั้ง · checksum กันไฟล์ซ้ำ · ตรวจคีย์หลักก่อนลง HDFS · allowlist URL แบบ fail-closed · SQL อ่านอย่างเดียว · จำกัดขนาดไฟล์ · สถานะ QUEUED→RUNNING→SUCCEEDED/FAILED/SKIPPED

**พูดอย่างไรให้ตรงความจริง**
- ยัง **ไม่มีตารางกระทบยอด Source → Raw** ที่นับอิสระทั้งสองฝั่งและเทียบรายแถว มี 1 หลักฐานที่ตัวเลขต้นทางตรงปลายทางคือ PostgreSQL 10,100 แถว
- ห้ามใช้ `total_records` เป็น "จำนวนที่ extract ได้" เพราะเป็นค่าหลัง transform (ชุดประเมิน 10,100 → `total_records` 10,000)
- `sdoqap_runs` ไม่เก็บจำนวนแถวต้นทาง/แถว raw
- ไม่มีบันทึกความล้มเหลวก่อนลง HDFS จึงคำนวณ Extraction Success Rate ไม่ได้ (ได้เฉพาะ 12/15 ของไฟล์ที่ลงทะเบียนแล้ว = 80% *(คำนวณ)* และไม่ควรเรียกว่าอัตราสำเร็จของ extraction)

**พูดอย่างไรให้ตรงความจริง**

| อ้างอิงที่ถูกต้อง (`clean_dataset.csv`) | 10,000 | 77.91 | 99.72% | 28 |
| สกปรก ก่อน ETL | 10,100 | 77.83 | 98.94% | 104 |
| หลัง ETL (Spark) | 9,370 | 78.00 | 99.95% | 5 |

**ช่องทางใช้ประโยชน์ที่ระบบมี**: Create Dashboard (AI) — เลือกจาก active layer เท่านั้น, LLM เลือกเฉพาะ spec ส่วนค่าทุกตัวคำนวณด้วย pandas, LLM ได้เห็นเฉพาะ schema/profile ไม่เห็นแถวข้อมูล · Trust-Check API · export CSV · Executive Dashboard

**พูดอย่างไรให้ตรงความจริง**
- ค่าเฉลี่ยหลัง ETL ใกล้ความจริงขึ้นเล็กน้อย (78.00 เทียบ 77.91) แต่รายชื่อนักศึกษาที่ต้องติดตามเหลือ **5 จาก 28 คน** เพราะคนที่สอบตกจริงถูกกักกันเป็น anomaly ถ้าสไลด์โชว์แค่ "อัตราผ่าน 99.95%" กรรมการที่เทียบกับข้อมูลอ้างอิงจะพบความต่าง
- ยังไม่มีตัววัดของ Create Dashboard (ความถูกต้องของ KPI, เวลา generate, อัตรา AI/rules) ในไฟล์หลักฐานที่ commit อยู่ ต้องรันแล้วเก็บเองถ้าจะอ้างตัวเลข
- Executive Dashboard มีบั๊กที่บันทึกไว้ (F-21/22/23: missing/duplicate/invalid แสดง 0% ทั้งที่กักกัน 169,851 แถว) ใช้ Create Dashboard เป็นหลักฐานหลักแทน
- การวิเคราะห์เป็นระดับค่าเฉลี่ย/อัตราผ่าน บนข้อมูลสังเคราะห์
