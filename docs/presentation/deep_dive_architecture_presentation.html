8-Layer Architectural Blueprint: End-to-End Data Lifecycle

การแบ่งระดับชั้นสถาปัตยกรรมตามวงจรชีวิตของข้อมูลตั้งแต่การรับเข้าจนถึงการนำไปใช้ประโยชน์

Slide 03 · Pre-Flight Ingestion & Schema Drift

Layer 1 & 2: ประตูด่านหน้าและธรรมาภิบาลโครงสร้าง

ระบบคัดกรองความปลอดภัยของข้อมูลเข้า ป้องกันการล้มเหลวแบบเงียบ และจัดการ Schema Drift แบบอัตโนมัติ

Layer 1: Multi-Source Ingestion Hub

  • Batch CSV/Excel: SHA-256 Checksum ป้องกันไฟล์ซ้ำ, ตรวจคีย์หลักก่อนลง HDFS (รองรับ utf-8-sig)
  • RDBMS Ingestion: คำสั่ง SQL SELECT (Read-Only) จำกัดโฮสต์ใน RDBMS_ALLOWED_HOSTS
  • REST API Ingestion: รองรับ data.go.th และ Fail-Closed ผ่าน API_INGEST_ALLOWED_HOSTS
  • Trigger Daemon: พอร์ต 8099 รับคิว FIFO ควบคุมด้วย X-Trigger-Secret

Layer 2: Schema Drift Pre-Flight Gate

  • Scoring Mechanism: คอลัมน์ใหม่ +1, คอลัมน์สูญหาย +5, ชนิดข้อมูลไม่ตรง +5
  • Safe Drift Auto-Evolution: กรณีพบเฉพาะคอลัมน์ใหม่ ร่วมกับนโยบาย policy_allow_new อัปเดต Registry ทันที
  • Missing Columns: เติมค่า NULL อัตโนมัติ พร้อมส่ง Critical Alert (Slack/LINE Notify)
  • Type Mismatch: แคสต์เป็น String ชั่วคราวป้องกันไปป์ไลน์หยุดชะงัก
  • Semantic PII Guard: ตั้งธง PII ภาษาไทย-อังกฤษ เพื่อตัดออกจาก Export CSV และห้ามส่งให้ LLM
Incoming Data ──► [ Checksum & PK Check ] ──► [ HDFS /data/raw/ ] ──► [ Schema Drift Evaluator ] ├── Safe (New cols) ──► Auto-Evolve Schema └── Broken (Missing) ──► Fill NULL + Send Alert
Slide 04 · Compute Dual-Engine Architecture

Layer 3: สถาปัตยกรรมเอนจินคู่ (Dual-Engine Architecture)

แยกหน้าที่ระหว่างการตอบสนองทันทีบนหน้าพอร์ทัล ออกจากการประมวลผลขนาดใหญ่แบบขนานบนคลัสเตอร์

มิติเปรียบเทียบ 1. Interactive Whitebox Engine 2. Distributed Spark Batch Engine
เทคโนโลยีหลัก FastAPI, Python 3.10, Pandas Apache Spark 3.4.1 (Bitnami Image)
ลักษณะการทำงาน Synchronous In-Memory Profiling Distributed Batch Compute (Master-Worker)
ช่องทางเรียกใช้งาน /api/v1/whitebox/*, /rules Spark Trigger Daemon (พอร์ต 8099)
บทบาททางสถาปัตยกรรม สร้างข้อเสนอกฎ 3 ด้านทันที และตรวจ Referential Integrity ข้ามตาราง ดำเนินการครบ 21 Stages, คัดแยกแถวเสีย และบันทึก Delta Lake
เกณฑ์ Outlier โปรไฟล์นับด้วย $1.5 \times \text{IQR}$ และเสนอกฎ auto_iqr ที่ $3.0 \times \text{IQR}$ (Tukey Far-Out) ตรวจจับความผิดปกติด้วย Tukey IQR $1.5 \times \text{IQR}$ และ Z-Score $3\sigma$
ข้อเสนอกฎ 3 ด้านของ Whitebox Engine: (1) Completeness สำหรับคอลัมน์สำคัญ (2) Non-Negative Range >= 0 สำหรับยอดขายและสต็อก (3) Tukey Outer Fence ($3.0 \times \text{IQR}$) สำหรับดักจับค่าหลุดโลกที่ชัดเจน

Slide 06 · Storage Silver Medallion Dual-Zone

Layer 4: สถาปัตยกรรมจัดเก็บข้อมูล Silver Dual-Zone บน Delta Lake

การคัดแยกข้อมูลดีและข้อมูลเสียออกเป็น 2 โซนอิสระ รับประกัน ACID Transactions และคุณสมบัติ Idempotency

Active Store (Clean Silver Zone)

Delta Lake
  • ตำแหน่ง: /data/active/<table_name>/ บน HDFS
  • วิธีการเขียน: ใช้คำสั่ง MERGE INTO (Upsert) ตาม Primary Key
  • ACID Transactions: ป้องกันข้อมูลชนกันระหว่างเขียน รองรับ Concurrent Writes
  • Idempotency: รันซ้ำกี่ครั้งก็ได้ผลถูกต้องเท่าเดิม ไม่เกิดแถวข้อมูลเบิ้ลซ้ำ
  • พร้อมใช้งาน: ส่งมอบต่อให้ Data Warehouse, BI Dashboard และ AI Models

Quarantine Store (Error Isolation Zone)

Delta Lake DLQ
  • ตำแหน่ง: /data/quarantine/<table_name>/ บน HDFS
  • วิธีการเขียน: ลบข้อมูลเก่าของ ingest_id ออกก่อน แล้ว Append ใหม่
  • พาร์ทิชัน: แบ่งตาม run_id ทำหน้าที่เป็น Dead-Letter Queue
  • เมทาดาต้าแถวเสีย: รักษาค่าเดิมครบ พร้อมฟิลด์ run_id, ingest_id, และ reject_reason (เชื่อมหลายสาเหตุด้วย ; )
  • ไม่สูญหาย: ข้อมูลเสียไม่ถูกกลืนทิ้ง นำไปกระทบยอดและตรวจสอบย้อนหลังได้ 100%
สมดุลการกระทบยอดข้อมูล: Inbound Volume = Active Rows + Quarantined Rows + Pre-Clean Duplicate Rows
Slide 07 · Observability Serving & Trust-Check

Layer 5 & 6: การสังเกตการณ์ การให้บริการ API และการควบคุมความเสี่ยง

การจัดเก็บดัชนี Telemetry บน Elasticsearch และการให้บริการ API พร้อมเกราะป้องกัน Trust-Check

Layer 5: Gold Observability Telemetry

  • Elasticsearch 8.10.2: จัดเก็บดัชนีชี้วัดเพื่อการสืบค้นแบบมิลลิวินาที
    • sdoqap_quality_runs: สถิติรอบรัน, อัตรากักกัน, คะแนนคุณภาพ
    • sdoqap_pipeline_runs: เวลาประมวลผล, Latency, สถานะ SLA
    • sdoqap_upstream_remediations: บัตรงานแก้ไขปัญหาต้นทาง
    • sdoqap_schema_proposals: ประวัติข้อเสนอโครงสร้างข้อมูล
  • Kibana (5601): ตรวจสอบ Log เชิงลึกและค้นหาเอกสารต้นฉบับ
  • Grafana (3002): แดชบอร์ด Time-Series ติดตาม Throughput คลัสเตอร์

Layer 6: Serving API & Domain Mapping

  • FastAPI Serving: ให้บริการ REST API ที่พอร์ต 8002 (ภายนอก) / 8000 (ภายใน)
  • 5-Domain Area Mapping: โครงสร้าง AREA_TABLE_MAPPING จับคู่ชื่อตารางเข้าสู่ 5 สายธุรกิจ: sales, customer, operations, reporting, และ finance
  • Trust-Check Gate API: GET /api/v1/lineage/{table_name}/trust-check
    • ประเมิน 3 ปัจจัย: คะแนนผ่านเกณฑ์, ไร้ Proposal ค้าง และตรวจสำเร็จ
    • ตอบกลับ is_safe_to_consume เป็นที่ปรึกษาเชิงคุณภาพให้ระบบปลายทาง
Spark Telemetry ──► Elasticsearch ──┬──► Kibana :5601 & Grafana :3002 └──► FastAPI :8002 ──► 5-Domain Filtering & Trust-Check API
Slide 08 · Financial 3D COPDQ Model

เอนจินประเมินความเสียหายทางการเงินจากข้อมูลด้อยคุณภาพ (COPDQ)

แปลงข้อผิดพลาดทางเทคนิคให้เป็นมูลค่าความเสียหายทางการเงินและต้นทุนการจัดการที่ฝ่ายบริหารเข้าใจได้ทันที

1. Cost of Correction

ต้นทุนแรงงานและรันซ้ำ

$2.00 / แถวกักกัน

ต้นทุนด้านวิศวกรรมและการคำนวณในการดึงข้อมูลที่ติดกักกันกลับมาล้างและประมวลผลใหม่

2. Cost of Lost Opportunity

มูลค่ายอดขายที่ถูกกักกันจริง

Σ Actual Monetary Value

ผลรวมยอดขายจริงจากแถวที่ติดกักกัน (เช่น คอลัมน์ total_sales, price) หากไม่มีใช้โมเดล 5% × $50

3. Cost of Risk & Compliance

ความเสี่ยงโครงสร้างตาราง

Rows × drift_severity

มูลค่าความเสี่ยงจากการละเมิด SLA และการเปลี่ยนแปลงของโครงสร้างข้อมูลในระบบ

Gartner TCO Operational Waste: ในโหมดการกระทบยอดปริมาณข้อมูล หากไม่มีคอลัมน์การเงิน คิดต้นทุนวิศวกรรมจัดการข้อมูลเสียคงที่ที่ $2.50 ต่อแถว
การแสดงผลค่าเงิน: คำนวณเป็นดอลลาร์สหรัฐ (USD) เป็นหลัก และแปลงเป็นเงินบาท (THB) ด้วยอัตราแลกเปลี่ยนอ้างอิงคงที่ 36.5 THB/USD
Slide 09 · Closed-Loop Portal & Auto-Healing

Layer 7 & 8: พอร์ทัลกลางและวงจรปิดแก้ไขปัญหาถึงต้นน้ำ

การแสดงผลที่ตอบสนองสองทางไร้ความหน่วง พร้อมระบบปฏิบัติการแก้ไขปัญหาถึงระบบต้นทางแบบอัตโนมัติ

Layer 7: Central Portal UI & State Sync

  • React 18 & Zustand Store: สลับ 4 มุมมอง (Executive, Business, Quality, Dashboard Builder)
  • Two-Way State Sync: เมื่อคลิกการ์ดแผนก ตัวแปร selectedAreaFilter จะซิงก์ดรอปดาวน์และกรองข้อมูลทั้งแดชบอร์ดพร้อมกันทันที
  • Stream Simulation: DataFlowStreamChart.jsx จำลอง Throughput $1,150 - 1,800$ แถว/วินาที สาธิตพลวัตของข้อมูลสด

Layer 8: Closed-Loop Upstream Healing

  • Ticket Generation: AI Advisory วิเคราะห์แถวเสีย ออกตั๋วงานระบุ target_system และ remediation_action
  • วิศวกรแก้ปัญหาที่ต้นทาง: ทีมงานปรับปรุงโค้ดหรือชุดข้อมูลต้นน้ำ
  • Auto-Trigger Reprocessing: เมื่อกดปุ่ม Resolve บนหน้าเว็บ ระบบเรียก POST .../resolve แล้วส่งคำสั่งต่อไปยัง POST http://spark-master:8099/retry ทันที
  • Transparent Feedback: หน้าเว็บได้รับค่า spark_triggered: true ยืนยันการสั่งรันใหม่
[ Spark พบแถวเสีย ] ──► [ AI สร้าง Ticket ] ──► [ วิศวกรแก้ต้นทาง ] ──► [ กด Resolve ] ──► [ POST :8099/retry ] ──► [ Spark รันใหม่ทันที ]
