### 1. จำนวนแหล่งข้อมูลและปริมาณข้อมูล (10) — 6.5

**สิ่งที่มีจริง**
- ตัวเชื่อม 4 ชนิดมีโค้ดและผ่านการทดสอบกับระบบจริง: ไฟล์ CSV/Excel, REST API (รวม data.go.th), PostgreSQL แบบ read-only, Reddit → Kafka → Spark Structured Streaming (`services/api/app/api/pipeline.py`, `services/spark/streaming_job.py`; รายงานทดสอบ T2–T5)
- ปริมาณที่ประมวลผลผ่าน Spark สะสม 3,576,836 แถว 183 รอบ (ค่าจาก `GET /api/v1/kpi/stats` วันที่ 2026-10-02) รอบใหญ่สุด 990,100 แถว

**สิ่งที่ขาด**
- `docs/evaluation/evidence/d-source-inventory.json` บันทึกการนำเข้าจริงแยกตามแหล่งไว้แค่ `file` 14 ครั้ง และ `build_rubric_report.py` ไม่ได้พิมพ์ตารางนี้ลงรายงานเลย รายงานจึงแสดง "ตัวเชื่อมที่มี" ไม่ใช่ "แหล่งที่ใช้จริง"
- ปริมาณของแหล่งที่ไม่ใช่ไฟล์น้อยมาก: `gov_data` (data.go.th) 11 แถว แต่รันซ้ำ 108 รอบ, `pg_smoketest` 1 แถว, `smoketest_api` 10 แถว, Reddit 56 ข้อความ, ตาราง RDBMS 500 แถวของการทดสอบถูกลบไปแล้ว
- ปริมาณรวมถูกดันด้วยสำเนา: `bench_*` (สำเนาของชุดประเมินชุดเดียว) รวมราว 1.6 ล้านแถว และ `customer_data` กับ `customer_churn_full` คือไฟล์ Kaggle ไฟล์เดียวกัน (440,833 แถว) สองชื่อตาราง ข้อความ "31 ไฟล์ 651,466 แถว" ในรายงานนับไฟล์ที่เป็นข้อมูลชุดเดียวกันซ้ำ (clean/dirty/ground truth/answer key) ชุดข้อมูลที่ต่างกันจริงมีราว 6 ชุด
- แต่ละแหล่งลงตารางของตัวเองแยกกัน ไม่มีการรวมหลายแหล่งเข้าโมเดลข้อมูลเดียวในเส้นทาง Spark (การ join 2 ตารางมีเฉพาะในเอนจินโต้ตอบ)
- `data/stress/100000 Sales Records.csv` เป็นโฟลเดอร์ว่าง และชุด Olist มีแค่ 1 จาก 9 ไฟล์

**ทำอย่างไรให้ขึ้น** Task 2 ของแผน: นำเข้าจริงจาก Postgres 10,000 แถว, API, และ stream แล้วให้รายงานพิมพ์ตารางการนำเข้าแยกตามแหล่ง และพูดตรงๆ ว่าชุดขยายเป็นสำเนา

### 2. จำนวนกระบวนการในการจัดการข้อมูล (15) — 12

**สิ่งที่มีจริง** 21 stage ลงทะเบียนใน `services/spark/sdoqap/stages/` จับเวลาแยกทุกตัว มี unit test 60 ข้อ (ผลวันที่ 2026-10-01 ผมไม่ได้รันซ้ำวันนี้) บวกขั้นนำเข้า (checksum, ตรวจคีย์, คิว), Gold layer, streaming

**สิ่งที่ขาด**
- ในรอบประเมิน (`d-batch-run.json`) มี 6 stage ที่ใช้เวลา ≤ 0.007 วินาที คือไม่ได้ทำอะไรกับชุดข้อมูลนี้: `schema_drift`, `standardize_dates`, `standardize_categories`, `anomaly_induced` (0.0), `column_filter`, `copdq` (0.0) กรรมการที่อ่านตารางเวลาจะเห็น
- ไม่มีจำนวนแถวเข้า/ออกราย stage มีแต่เวลา จึงพิสูจน์ไม่ได้ว่าแต่ละ stage เปลี่ยนข้อมูลอย่างไร
- การตัดแถวซ้ำเกิดสองที่ (`auto_clean` และ `dedup`) และ 5 stage ช่วง post_load เป็นการคำนวณตัวชี้วัด ไม่ใช่การจัดการข้อมูล ถ้ากรรมการนับเข้ม จำนวนจะน้อยกว่า 21
- ไม่มีเครื่องมือ orchestration มาตรฐาน (ใช้ daemon ที่เขียนเอง + n8n)

**ทำอย่างไรให้ขึ้น** ในสไลด์จัดเป็น 5 กลุ่มแทนการอ้างเลข 21 ลอยๆ และสาธิต stage ที่เงียบด้วยข้อมูลที่ทำให้มันทำงาน เช่น ไฟล์ที่เพิ่มคอลัมน์สำหรับ `schema_drift` (รายงานทดสอบ T8.1 ทำแล้ว: ได้ proposal สถานะ PENDING และ trust-check ตอบ HALT_INGEST)

### 3. Data extraction (10) — 7.5

**สิ่งที่มีจริง** `ingest_id` ต่อการนำเข้า, โฟลเดอร์ raw แยกกัน, ตรวจไฟล์ซ้ำด้วย checksum, ตรวจคีย์หลักก่อนลง HDFS, allowlist URL แบบ fail-closed, SQL read-only + เพดานจำนวนแถว, คิวต่อตาราง, สถานะ QUEUED→RUNNING→SUCCEEDED/FAILED ผลทดสอบ e2e ผ่าน 3 ข้อ (`b-e2e-ingest-check.txt`)

**สิ่งที่ขาด**
- หลักฐาน "จำนวนแถวที่ดึงได้ = จำนวนแถวต้นทาง" มีเฉพาะไฟล์ ไม่มีของ API/RDBMS ในรายงานเกณฑ์
- ปุ่ม "เชื่อมต่อและตรวจข้อมูล" ของแท็บ Database/API/Stream เรียก `/whitebox/ingest-source` ซึ่งเป็นโหมดสาธิต (`services/ui/src/pages/Ingestion.jsx:735,776,813`) การนำเข้าจริงอยู่ที่ปุ่ม submit ของฟอร์มเดียวกัน ถ้ากดผิดปุ่มตอนสาธิตจะขึ้นคำว่า "โหมดสาธิต"
- การเดาคีย์หลักเป็น heuristic (`services/spark/sdoqap/common/keys.py`) เคยทำให้ 1,030 แถวเหลือ 250 แบบเงียบๆ (F-2 แก้แล้ว) ตารางใหม่ที่ไม่ได้ลงทะเบียนคีย์ยังพึ่งการเดา
- ดึงทั้งก้อนทุกครั้ง ไม่มี incremental/CDC (`gov_data` 108 รอบของ 11 แถวเดิม)
- n8n node "Query Sales Records" ล้มทุก 30 นาทีเพราะไม่มี credential Postgres (รายงานทดสอบ หมายเหตุ F-16)

### 4. Data transformation (10) — 7

**สิ่งที่มีจริง** วัด detection เทียบ ground truth: recall 1.0, precision 0.9589, accuracy 0.997 (TP 700, FP 30, FN 0, TN 9,370) เทียบ IQR 1.5 กับ 3.0 และ golden test ก่อน/หลัง refactor ตรงกัน

**สิ่งที่ขาด** (ตรวจเองจาก `data/evaluation/output/quarantine.csv` เทียบ `ground_truth.csv`)
- ชุดวัดผลเป็นข้อมูลสังเคราะห์ชุดเดียว ใส่ปัญหา 4 ชนิดที่รู้ล่วงหน้า กฎถูกตั้งให้เข้ากับชุดนี้ จึงยังไม่รู้ว่าใช้กับข้อมูลจริงได้ดีแค่ไหน
- **คะแนนที่ว่างไม่ได้ถูกจับในฐานะ "ค่าว่าง"** กฎ `remediation_rules` ของตารางนี้เติม `score = 0` ก่อน (`services/spark/rules_config.json` บล็อก `student_course_scores`) แล้ว IQR จับ 0 เป็น outlier เหตุผลที่บันทึกคือ `score=0.0 (expected [32.0000, 123.0000])` (297 แถว) ไม่ใช่ "missing" ถ้าคะแนนกระจายกว้างจน 0 อยู่ในช่วง ค่าว่างจะกลายเป็นคะแนน 0 ในข้อมูลสะอาด กฎ `calculate: study_hours * 1.5` ที่อยู่ถัดไปไม่มีวันทำงานเพราะค่าว่างถูกเติมไปแล้ว
- **False positive 30 แถว มี 21 แถวเป็นนักศึกษาที่ได้คะแนน 37–49 จริง** ถูก Z-score > 3σ กักกัน อีก 9–10 แถวเป็น study_hours 11–12 ชั่วโมง เกณฑ์ 3σ เขียนตายตัวใน `services/spark/sdoqap/stages/anomaly.py` ตั้งค่ารายคอลัมน์ไม่ได้
- แถวซ้ำ 100 แถวถูก `auto_clean` ตัดทิ้งโดยไม่เข้า quarantine ตัววัดนับว่า "ตรวจพบ" แต่ตรวจย้อนหลังไม่ได้ว่าแถวไหนถูกทิ้ง
- สองเอนจินให้ผลต่างกันกับไฟล์เดียวกัน: เอนจินโต้ตอบ 9,400 สะอาด / 100 รอตรวจ / 600 กักกัน (precision 100%) ส่วน Spark 9,370 / 630 และ Spark ไม่มีโซน "รอคนตรวจ"
- การแปลงส่วนใหญ่คือการคัดกรอง ไม่มีการ join/สรุป/จัดรูปข้อมูลธุรกิจในเส้นทาง Spark

### 5. Data loading (5) — 3

**สิ่งที่มีจริง** เขียน quarantine แบบ idempotent ก่อน Delta MERGE, ย้าย raw ไป archive, lock มี heartbeat, ยอดตรงกัน 10,000 = 9,370 + 630 ผล benchmark จริงเคยวัดได้ (commit `3013226`): 10K 66.2 วินาที, 100K 85.5, 500K 203.4, 1M 414.2 (ในเอนจิน) ซึ่งผ่านข้อกำหนด TOR "ล้านแถวไม่เกิน 10 นาที"

**สิ่งที่ขาด**
- **`docs/evaluation/rubric-mapping.md` ที่ commit อยู่แสดงตาราง benchmark เป็น `FAILED` ทั้ง 4 ขนาด** เพราะ commit `17b3024` เขียนทับ `d-scale.json` ด้วยผลรันที่ล้มใน 1 วินาที สาเหตุที่ยืนยันแล้ว: เมื่อเรียก Python จาก PowerShell `shutil.which("bash")` ได้ `C:\Windows\system32\bash.EXE` (ตัวเรียก WSL) ไม่ใช่ Git Bash ถ้ากรรมการเปิดรายงานนี้จะเห็นว่าระบบโหลดข้อมูลไม่ผ่านเลย
- ไฟล์ต้นทาง 10,100 แถว แต่ยอดที่โหลดกระทบได้คือ 10,000 ส่วนต่าง 100 แถวไม่มีที่เก็บ
- ปลายทางคือ Delta บน HDFS กับ Elasticsearch ไม่มีฐานข้อมูลให้ผู้ใช้ปลายทาง query ข้อมูลธุรกิจโดยตรง (ใช้ export CSV)

- Grafana ไม่มี dashboard ที่ provision ไว้ (รายงานทดสอบ T12.4)

### 7. ขอบเขตโครงงานน่าสนใจ/แปลกใหม่ (5) — 4

จุดแข็ง: รวม ingestion หลายชนิด + quality gate + quarantine + governance + อธิบายเหตุผลได้ทุกขั้น (white-box) และรองรับภาษาไทย/พ.ศ. จุดที่ต้องระวัง: แนวคิดหลักมีในเครื่องมือเปิด (Great Expectations, Deequ, Soda, Monte Carlo ซึ่ง TOR เองก็อ้าง) ต้องตอบให้ได้ว่าต่างตรงไหน

### 8. Component/Feature ใช้นวัตกรรม (5) — 3

- มีจริงในโค้ด: เกณฑ์ปรับตามประวัติ, PSI + EMA, Decision Tree เสนอกฎ, LLM เสนอกฎผ่านการอนุมัติของคน, hybrid similarity ภาษาไทย, schema drift gate
- แต่**ยังไม่ได้วัดว่าแต่ละตัวช่วยได้เท่าไร** (`docs/reports/ETL_Change_Summary.html` ก็เขียนยอมรับไว้) และในรอบประเมิน `anomaly_induced` กับ `copdq` ใช้เวลา 0.0 วินาที คือไม่ได้ทำงาน
- `POST /api/v1/rules/ai-proposals/reset` ไม่เรียก LLM คืนข้อเสนอตัวอย่างที่เขียนตายตัว (`is_example: true`) ส่วน `POST /api/v1/rules/ai-proposals/generate` (ปุ่ม "วิเคราะห์ด้วย AI", แก้ F-6 เมื่อ 2026-10-02) วิเคราะห์แถวกักกันจริงด้วย Groq → Ollama → กฎคงที่ และเก็บเป็น `PROPOSED` ส่วนที่ใช้ LLM จริงอีกจุดคือ AI context ในเอนจินโต้ตอบ (Groq)
- COPDQ ใช้ค่าคงที่ที่สมมติ ($2 ต่อแถวสำหรับค่าแก้ไข, 5% × $50 สำหรับโอกาสที่เสียเมื่อตารางไม่มีคอลัมน์มูลค่าเงิน — ดู `docs/whitebox-report/07-copdq-financial-impact.md`) กับชุดประเมินซึ่งไม่มีคอลัมน์เงิน stage `copdq` จึงได้ 0

### 9. ดัดแปลงเทคนิคที่มีอยู่ได้เหมาะสม (5) — 3.5

จุดแข็ง: เทียบ IQR 1.5 กับ 3.0 ด้วยตัวเลข (FP 101 → 30), Z-score มีพื้น std, Delta MERGE, n-gram cosine, แปลง พ.ศ. จุดอ่อน: Z-score 3σ กับคะแนนสอบที่มีขอบเขต 0–100 อยู่แล้วเป็นการใช้เทคนิคซ้ำซ้อนและทำให้ตัดคนสอบตก, การเติม 0 ให้คะแนนที่ว่างไม่เหมาะกับข้อมูลเกรด, พยากรณ์ OLS จากจุดข้อมูลน้อย
