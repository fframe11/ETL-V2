Slide 01 · Pipeline Blueprint Sequential Deterministic DAG Zero Silent Drop

สถาปัตยกรรม Data Transformation: จาก "4 ประตูนามธรรม" สู่ "Sequential Deterministic DAG"

กลไกการตรวจสภาพ คัดแยก และแปลงสภาพข้อมูลระดับแถวบน Apache Spark & Delta Lake ควบคุมด้วย RunContext 13 Stages ต่อเนื่อง

PILLAR 1
Deterministic Execution

ควบคุมลำดับการประมวลผลเด็ดขาดผ่าน plan.py ด้วย @stage แบ่งเป็น ALIGN (1 Stage) และ TRANSFORM (12 Stages) ปราศจากการเรียกสลับลำดับ

PILLAR 2
Zero Silent Drop

ข้อมูลทุกแถวที่ผิดพลาดจะถูกระบุเหตุผลใน reject_reason และส่งเข้าสู่ Silver Quarantine Lake ไม่มีการ Drop แถวทิ้งอย่างเงียบๆ

PILLAR 3
Volume Reconciliation

รับประกันสมการความสมดุล 100%: ยอด Raw นำเข้า เท่ากับยอด Clean ใน Active + ยอด Quarantine + ยอดตัดซ้ำใน Auto-Clean พอดีทุกรอบ

Slide 02 · Stage 01 schema_align Smart Type Promotion

ขั้นตอนการจัดระเบียบโครงสร้างและชนิดข้อมูล (Stage 1: schema_align)

ปรับชื่อคอลัมน์สู่มาตรฐาน สร้าง Dynamic Composite Key ด้วย MD5 และใช้นวัตกรรม Smart Type Promotion ป้องกัน Data Loss

4 กลไกการจัดระเบียบข้อมูล
  • Column Sanitization: ตัด Whitespace, ลบอักขระพิเศษ, ทำ Fuzzy Match กับ schema_spec
  • Dynamic row_hash: รวบคอลัมน์คั่นด้วย || แล้ว Hash ด้วย MD5 สำหรับตารางที่ไร้ Primary Key
  • Smart Type Promotion: สแกนค่าด้วย Regex \.[0-9]*[1-9]+ หาก Integer มีทศนิยมปน จะเลื่อนเป็น DoubleType ทันทีเพื่อกันค่ากลายเป็น Null
  • Robust Timestamp Parsing: รองรับทั้งมาตรฐาน ISO, Slash delimiter และ Unix Epoch (sec/ms)
กรณีศึกษา: ป้องกัน Data Truncation
Input: Column "Total Price (THB)" with value "1500.75" Schema Registered: IntegerType │ ▼ [ Regex Scan: r"\.[0-9]*[1-9]+" matched non-zero decimals ] │ ▼ Action: Promotes IntegerType ──► DoubleType Result: Preserves 1500.75 without truncation/nullification!
Slide 03 · Stage 02 schema_drift Self-Healing & Governance Gate

การตรวจจับและจัดการความเปลี่ยนแปลงโครงสร้าง (Stage 2: schema_drift)

จำแนกความรุนแรงของ Drift (Severity Scoring) แยกแยะการอนุมัติอัตโนมัติ (Self-Healing) กับการกักกันรอคนอนุมัติ (Governance Gate)

SEVERITY: LOW (+1)
New Columns

พบคอลัมน์ใหม่ที่เพิ่มเข้ามา หากเปิด allow_new=True ระบบจะทำ Schema Evolution ลง Delta Lake ให้โดยอัตโนมัติ

SEVERITY: CRITICAL (+5)
Missing Columns

คอลัมน์สำคัญจากต้นทางหายไป ระบบจะ Auto-heal ด้วยค่า Null ตามชนิดคอลัมน์ พร้อมตั้งสถานะ PENDING ส่ง Webhook เตือน

SEVERITY: CRITICAL (+5)
Type Mismatch

ชนิดข้อมูลไม่ตรง บังคับ Coerce เป็น StringType ชั่วคราวเพื่อป้องกัน Engine หยุดทำงาน และกักกันรอบนั้นทันที

[ Inbound Schema vs. Registered Schema ] ──► Compute Drift Severity │ ├─► Severity == 1 (Only New Cols & allow_new=True) ──► [ Auto-Approved Evolution ] │ └─► Severity >= 5 (Missing Col / Type Mismatch) ──► [ Fill Null / Coerce String ] │ ▼ [ Status: PENDING / REJECTED ] [ Slack Alert via n8n Webhook ]
Slide 04 · Stages 03 & 04 auto_clean & validation Safe DSL Remediation

การเยียวยาด้วยกฎและการตรวจความถูกต้องระดับแถว (Stages 3 & 4)

ประมวลผลกฎ DSL เยียวยาข้อมูลอย่างปลอดภัยใน Stage 3 ควบคู่กับการสแกนความถูกต้องระดับแถวใน Stage 4 พร้อมผูก reject_reason

Stage 3: auto_clean (Safe DSL)
  • รองรับ 4 Actions: fillna, calculate, cast, filter
  • Regex Sandbox ป้องกัน Code Injection: อนุญาตเฉพาะอักขระ ตัวเลข และ Math Operators
  • ตัดแถวซ้ำที่มี Primary Key สมบูรณ์ล่วงหน้า และบันทึกยอด dup_resolved
Stage 4: validation (Row-Level Checks)
  • ตรวจ PK ค่าว่าง ──► ระบุเหตุผล missing_primary_key
  • ตรวจค่าว่างในคอลัมน์บังคับ ──► ระบุเหตุผล null_value_in_<col>
  • ตรวจ Type ผิดพลาด ──► ระบุเหตุผล invalid_type_<col>
  • ตรวจวันที่ว่าง ──► ระบุเหตุผล missing_date
Incoming Data ──► [ Stage 3: auto_clean ] ──► Safe DSL Remediation & PK Deduplication │ ▼ [ Stage 4: validation ] ──► Comprehensive Null & Type Verification │ ┌───────────┴───────────┐ ▼ ▼ [ valid_df ] [ invalid_df ] (Ready for Stats) (Reason: "missing_primary_key", "null_value_in_score")
Slide 05 · Stages 05, 06 & 07 dedup & standardize Buddhist Era & Generic Categories

การกำจัดแถวซ้ำและการปรับมาตรฐานข้อมูล (Stages 5, 6 & 7)

ขจัดแถวซ้ำด้วย Left Anti-Join แยกแถวซ้ำไปกักกัน พร้อมแปลง พ.ศ. เป็น ค.ศ. อัตโนมัติ และจัดกลุ่มข้อมูลตามพจนานุกรม Elasticsearch

STAGE 05
Anti-Join Dedup

เรียงตาม date.desc() เพื่อคงเฉพาะแถวล่าสุด ส่วนแถวที่ซ้ำใช้ Left Anti-Join สกัดเข้า Quarantine ทันที

STAGE 06
พ.ศ. ──► ค.ศ. Auto

หากตรวจพบปี > 2500 ระบบหักลบด้วย 543 และปรับให้อยู่ในมาตรฐาน ISO YYYY-MM-DD ทันที

STAGE 07
ES Category Match

อ่านชุดคำสำคัญจาก Elasticsearch มาแมปคำสะกดผิดหรือชื่อสินค้าเข้าสู่ Category กลางโดยไม่ต้อง Hardcode

valid_df ──► Order by date DESC ──► dropDuplicates(subset=PK) ──► clean_df │ └──► Anti-Join with Original ──► duplicate_df (Reason: "duplicate_records") ──► Quarantine Input: "21 ก.ค. 2569" ──► Year (2569 > 2500) ──► [ Year - 543 ] ──► "2026-07-21" (ISO-8601) Input: "เสื้อยืดคอกลม cotton" ──► ES Keyword Match ──► Standard Category: "Apparel"
Slide 06 · Stages 08, 09 & 10 rules & anomaly Tukey IQR & 3-Sigma Gaussian

กฎธุรกิจและการตรวจจับความผิดปกติทางสถิติ (Stages 8, 9 & 10)

ผสานกฎขอบเขตธุรกิจ (Explicit Bounds) เข้ากับการตรวจจับทางสถิติ 2 โมเดล: Non-parametric Tukey IQR Fences และ Gaussian Z-Score

STAGE 08
Business Range Rules

ตรวจขอบเขตค่าคงที่ เช่น คะแนนสอบต้องอยู่ในช่วง 0 ถึง 100 หากหลุดช่วงจะระบุเหตุผล out_of_range_score

STAGE 09
Tukey's IQR Fences

คำนวณ \(Q_1, Q_3\) ด้วย approxQuantile แบบ \(O(N)\) ขอบเขต \([Q_1 - k\cdot\text{IQR}, Q_3 + k\cdot\text{IQR}]\) จับ Outlier สุดโต่ง

STAGE 10
3-Sigma Gaussian

ตรวจจับความเบี่ยงเบน \(Z = \frac{|X - \mu|}{\sigma} > 3.0\) ดักจับข้อผิดพลาดแบบ Unsupervised บนข้อมูลการแจกแจงปกติ

[ Business Bounds: range_rules ] Condition: score BETWEEN 0 AND 100 ──► If score = -10.0 or 145.0 ──► Flag Reason: "out_of_range_score" [ Statistical Fence: anomaly_iqr (Tukey's Fences) ] Data Distribution: [───(Q1 - 3.0*IQR)───[ Q1 | Median | Q3 ]───(Q3 + 3.0*IQR)───] * (Outlier: 48.0h!) Calculation: approxQuantile([0.25, 0.75]) ──► Rows outside fences ──► Flag Reason: "outlier_details" [ Gaussian Anomaly: anomaly_zscore ] Z-Score Formula: Z = |Value - Mean| / StdDev > 3.0σ ──► Flag Reason: "score_zscore=3.34 (val deviates > 3.0σ)"
Slide 07 · Stages 11, 12 & 13 ML & quarantine_assembly Zero Disk Spillage

กฎการเรียนรู้ Machine Learning และการประกอบโซนกักกัน (Stages 11, 12 & 13)

รวบกฎ Decision Tree ใน Stage 11, รวมและแคชชุดกักกันใน RAM ใน Stage 12, และทำความสะอาดคอลัมน์ภายในใน Stage 13

STAGE 11
ML Induced Rules

นำกฎจาก Decision Tree มารวมด้วย OR และประเมินผลด้วย F.expr() ดักจับความสัมพันธ์ข้ามหลายคอลัมน์

STAGE 12
quarantine_assembly

รวมทุก DataFrame ข้อผิดพลาดด้วย unionByName(allowMissingColumns=True) ผูก run_id และ .cache() ไว้ใน RAM

STAGE 13
column_filter

ตัดคอลัมน์ชั่วคราวทิ้งทั้งหมด (__row_id, reject_reason) คืนโครงสร้าง Clean 100% ให้ Silver Active

invalid_df (PK & Nulls) ────────┐ duplicate_df (Duplicates) ──────┼──► [ unionByName(allowMissingColumns=True) ] range_violation_df (Range) ─────┤ │ outlier_df (IQR Outliers) ──────┤ [ Add run_id & rejected_at ] unsupervised_df (Z-score) ──────┤ │ induced_outlier_df (Tree Rules) ┘ [ all_quarantined_write.cache() ] ──► Silver Quarantine (Delta Lake) clean_df (Passed all checks) ──► [ column_filter: Drop Temp Cols ] ──► [ clean_df.cache() ] ──► Silver Active (Delta MERGE)

"ใน Stage ที่ 5 ถึง 7 คือการยกระดับคุณภาพข้อมูลสู่มาตรฐานสากลครับ

ใน Stage 5 dedup เรานำข้อมูลที่ผ่านการตรวจเบื้องต้นมาคัดแถวซ้ำตามคีย์ธุรกิจ โดยจัดเรียงตามวันที่เพื่อเก็บเฉพาะเวอร์ชันล่าสุดไว้ ส่วนแถวซ้ำที่ถูกตัดออก เราไม่ได้โยนทิ้ง แต่ใช้เทคนิค Left Anti-Join ดึงออกมาเป็น duplicate_df เพื่อส่งเข้าโซนกักกัน

ใน Stage 6 standardize_dates เราแก้ปัญหาที่พบบ่อยมากในข้อมูลไทย คือการบันทึกปีเป็น พ.ศ. ระบบจะตรวจจับอัตโนมัติ ถ้าปีมากกว่า 2500 จะหักลบ 543 และปรับให้อยู่ในมาตรฐาน ISO YYYY-MM-DD ทันที

"มาถึง Stage 8 ถึง 10 ซึ่งเป็นการตรวจจับเชิงลึกด้านตัวเลขและสถิติครับ

Stage 8 range_rules เป็นกฎที่เจ้าของข้อมูลกำหนดอย่างชัดเจน เช่น คะแนนสอบของนักศึกษาต้องอยู่ระหว่าง 0 ถึง 100 หรือราคาต้องไม่ติดลบ แถวที่อยู่นอกช่วงจะถูกคัดออกทันที

แต่ในความเป็นจริง ข้อมูลบางอย่างอาจจะอยู่ในช่วงที่อนุญาต แต่เป็นค่าที่ผิดธรรมชาติ เช่น ชั่วโมงอ่านหนังสือต่อวัน ค่า 40 ชั่วโมงต่อวัน ไม่ติดลบ แต่เป็นไปไม่ได้ในความเป็นจริง เราจึงใช้ Stage 9 anomaly_iqr คำนวณหารั้ว Tukey Fences จากข้อมูลจริงด้วย approxQuantile ที่ทำงานเร็วมากในระดับ Big Data แถวที่หลุดขอบเขตรั้ว 1.5 เท่าหรือ 3.0 เท่าของ IQR จะถูกส่งเข้า Quarantine

"สไลด์สุดท้ายนี้คือหลักฐานยืนยันความถูกต้องทางวิศวกรรมของ DataServe ครับ เราไม่เพียงแค่นำเสนอทฤษฎีบนหน้ากระดาษ แต่เราขอยกผลลัพธ์จากการรันระบบจริงบน Spark และ Delta Lake มาแสดงให้เห็นครับ

ทางด้านซ้ายบน ทุกท่านจะเห็น Terminal Console Output จากการทดสอบระบบด้วยชุดข้อมูลคะแนนนักศึกษา 10,100 แถว ที่มี Ground Truth ความผิดปกติ 700 แถว ระบบสามารถตรวจพบข้อผิดพลาดได้ครบทุกประเภท ทั้งคะแนนว่าง 300 แถว, คะแนนหลุดช่วง 200 แถว, ชั่วโมงเรียนผิดปกติ 100 แถว และข้อมูลซ้ำ 100 แถว ส่งผลให้ได้ค่า Detection Recall เต็ม 1.0 หรือ 100% โดยไม่มีข้อผิดพลาดใดเล็ดลอดไปได้ (Zero False Negative) และมี Precision สูงถึง 95.89% เนื่องจากเราเปิดระบบดักจับสถิติ 3-Sigma เพิ่มเติมอีก 30 แถว

ทางด้านขวาบน คือภาพ Data Snapshot จากตาราง Silver Quarantine ของ Delta Lake จะเห็นได้ว่า ข้อมูลที่มีปัญหาไม่ได้ถูกโยนทิ้งอย่างไร้ร่องรอย แต่มีคอลัมน์ reject_reason ระบุชัดเจนว่าแถวนั้นติดปัญหาอะไร เช่น missing_score หรือ out_of_range ซึ่งทำให้ทีม Data หรือผู้ใช้ต้นน้ำสามารถเปิดดูและแก้ไขได้ทันที
