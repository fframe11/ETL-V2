# Create Dashboard: วิเคราะห์และข้อเสนอปรับปรุง

> เอกสารนี้วิเคราะห์จากโค้ดและข้อมูลจริงในระบบ ณ วันที่ 2026-10-06 ทุกหัวข้อแยกชัดเจนว่าอะไร **[มีแล้ว]** (อ้างอิงไฟล์) และอะไร **[ข้อเสนอ]** (ยังไม่มีในระบบ เป็นข้อเสนอสำหรับพัฒนาในอนาคต)
> ตัวอย่างชุดข้อมูลทั้งหมดดึงโปรไฟล์จากระบบที่รันอยู่จริง ไม่ใช่ข้อมูลสมมติ

## 0. สรุปสำหรับกรรมการ (อ่านหน้านี้หน้าเดียวพอ)

**ประโยคหลัก:** Create Dashboard ไม่ใช่ "AI ทำแดชบอร์ดแทนคน" แต่เป็น **ผู้ช่วยที่เปลี่ยนชุดข้อมูลที่ผ่านการตรวจคุณภาพแล้ว ให้เป็นแดชบอร์ดฉบับร่างได้ในไม่กี่นาที โดยอ้างอิงจากข้อมูลจริง** ทีม Analyst/BI ยังเป็นเจ้าของการตัดสินใจและแดชบอร์ดฉบับสุดท้าย

**ทำไมบริษัทที่มีทีม BI แล้วยังควรมี:**

| เหตุผล | หลักฐานในระบบ |
|---|---|
| ทีม BI ไม่ต้องเริ่มจากหน้าว่าง ได้ฉบับร่างทันทีหลังข้อมูลผ่านการตรวจ | ระบบสร้าง spec แล้วคำนวณตัวเลขให้ [มีแล้ว] |
| เห็นความน่าเชื่อถือของข้อมูลก่อนสร้าง ซึ่งเครื่องมือ BI ทั่วไปไม่บอก | ป้ายคะแนนคุณภาพและกล่องเตือนต่อชุดข้อมูล [มีแล้ว] |
| ตัวเลขทุกตัวคำนวณจากข้อมูลจริงด้วยโค้ด ไม่ใช่ AI เดา | `dashboard_compute.py` คำนวณด้วย pandas, AI ออกแบบแค่ spec [มีแล้ว] |
| ข้อมูลจริงไม่ออกไปนอกระบบ | prompt ส่งแค่ชื่อคอลัมน์ ชนิด และสถิติ ไม่ส่งแถวและไม่ส่งค่าหมวดหมู่ (`dashboard_llm.py:120-136`) [มีแล้ว] |
| ทำงานได้แม้ไม่มี AI | โหมดกฎอัตโนมัติ `fallback_spec` [มีแล้ว] |

**สิ่งที่ควรปรับ 3 อย่าง (เรียงตามคุ้มค่า):**
1. คำแนะนำในหน้า "ระบุความต้องการ" และ "ปรับด้วย AI" ต้องมาจากข้อมูลจริง ปัจจุบันเป็นข้อความตายตัว (หัวข้อ 3 และ 5)
2. เพิ่มทางเลือกกลุ่มผู้ใช้ "ดูแลคุณภาพข้อมูล" เพราะตรงกับแกนของ SDOQAP (หัวข้อ 4)
3. เปลี่ยนคำบรรยายและป้ายสถานะให้สื่อว่าเป็น "ฉบับร่างที่คนต้องตรวจ" (หัวข้อ 2)

## 1. บทบาทของ Create Dashboard

### 1.1 ยังจำเป็นหรือไม่

**จำเป็นในฐานะตัวช่วย ไม่จำเป็นในฐานะตัวแทนทีม** ถ้าขายว่า "AI สร้างแดชบอร์ดแทนทีม BI" จะอ่อนทันที เพราะแดชบอร์ดที่ระบบสร้างได้จำกัด:

- วิดเจ็ตมี 7 แบบ: kpi, bar, line, area, pie, donut, table (`dashboard_spec.py:15`)
- การคำนวณมี 6 แบบ: count, count_distinct, sum, avg, min, max (`dashboard_spec.py:16`)
- ไม่มี join ข้ามตาราง ไม่มีสูตรอัตราส่วน เช่น Profit Margin (อยู่ในแผน Semantic Layer ที่ยังไม่ได้ทำ)

แต่ระบบนี้มีสิ่งที่เครื่องมือ BI ทั่วไปไม่มี คือรู้ว่าข้อมูลชุดนั้น **ผ่านการตรวจแค่ไหน** ตรงนี้คือคุณค่าที่ไม่ซ้ำใคร

### 1.2 Positioning ที่แนะนำ

| อย่าพูด | ให้พูด |
|---|---|
| AI สร้างแดชบอร์ดแทนคน | AI ช่วยทีมทำฉบับร่างให้เร็วขึ้น คนตรวจและตัดสินใจ |
| สร้างแดชบอร์ดด้วย AI | สร้างฉบับร่างจากข้อมูลที่ผ่านการตรวจแล้ว |
| ไม่ต้องมีทีม BI | ทีม BI ได้จุดเริ่มต้นที่เร็วกว่า และรู้ว่าข้อมูลน่าเชื่อถือแค่ไหน |

ประโยคสำหรับสไลด์: **"จากข้อมูลที่ผ่าน Quality Gate ถึงแดชบอร์ดฉบับร่าง ในไม่กี่นาที ตัวเลขทุกตัวคำนวณจากข้อมูลจริง คนเป็นผู้ตัดสินใจ"**

### 1.3 AI ควรช่วยส่วนไหน

| งาน | สถานะ | หมายเหตุ |
|---|---|---|
| สร้างแดชบอร์ดฉบับร่าง (เลือกกราฟ KPI ตัวกรอง จัดวาง) | [มีแล้ว] | `dashboard_llm.generate_spec` พร้อม validate ทุกครั้ง |
| ปรับแดชบอร์ดตามคำสั่ง | [มีแล้ว] | `refine_spec` และแสดง "สิ่งที่เปลี่ยน" ด้วยโค้ดเทียบ spec (`diff_specs`) ไม่ใช่ AI เล่าเอง |
| เลือกประเภทกราฟให้เหมาะกับคอลัมน์ | [มีแล้ว] | อยู่ใน system prompt และตัวตรวจ spec |
| วิเคราะห์ชุดข้อมูลเบื้องต้น (โปรไฟล์) | [มีแล้ว] | ขั้น "ดูข้อมูล" แต่เป็นตารางสถิติ ยังไม่ตีความ |
| แนะนำคำถาม/KPI ที่เหมาะกับชุดข้อมูล | [ข้อเสนอ] | หัวข้อ 3 |
| แนะนำคำสั่งปรับที่เกี่ยวกับแดชบอร์ดปัจจุบัน | [ข้อเสนอ] | หัวข้อ 5 |
| ค้นหา Insight เช่น ค่าผิดปกติ การเปลี่ยนแปลงเด่น | [ข้อเสนอ] | ยังไม่มีในระบบ ควรทำหลัง 3 และ 5 และต้องคำนวณด้วยโค้ดแล้วให้ AI เรียบเรียง ไม่ให้ AI คิดตัวเลขเอง |

### 2.2 Flow ที่แนะนำ (เปลี่ยนน้อยที่สุด คงจำนวนขั้นเดิม 4 ขั้น)

| ขั้น | ชื่อเดิม | ชื่อใหม่ | เนื้อหา |
|---|---|---|---|
| 1 | เลือกชุดข้อมูล | เลือกชุดข้อมูล | ตารางเรียงตามอัปเดตล่าสุด พร้อมป้ายคุณภาพ [มีแล้ว] |
| 2 | ดูข้อมูล | ทำความเข้าใจข้อมูล | โปรไฟล์ [มีแล้ว] + กล่องเตือนคุณภาพ [มีแล้ว] + "สิ่งที่ระบบสังเกตเห็น" เช่น คอลัมน์ว่าง คอลัมน์ที่เป็นรหัส ช่วงวันที่ [ข้อเสนอ] |
| 3 | ระบุความต้องการ | เลือกสิ่งที่อยากเห็น | การ์ดคำแนะนำจากข้อมูลจริง เลือกได้หลายอัน + ช่องพิมพ์เองเป็นทางเลือก [ข้อเสนอ] |
| 4 | แดชบอร์ด | ฉบับร่างแดชบอร์ด | ป้าย "ฉบับร่าง ตรวจก่อนใช้" + แถบ "ตัวเลขคำนวณจากข้อมูลจริง" + คำแนะนำปรับแบบรู้บริบท [ข้อเสนอ] |

**คำบรรยายหน้า** (`config/pages.js:15`) เปลี่ยนจาก "สร้างแดชบอร์ดจากชุดข้อมูลด้วย AI" เป็น "สร้างแดชบอร์ดฉบับร่างจากข้อมูลที่ผ่านการตรวจคุณภาพ"

### 2.3 ช่อง "ระบุความต้องการ": พิมพ์เองอย่างเดียวหรือให้ AI แนะนำก่อน

**แนะนำให้ระบบแนะนำก่อน แล้วให้พิมพ์เองเป็นทางเลือก** เหตุผล:

- ผู้ใช้ส่วนใหญ่ไม่รู้ว่าชุดข้อมูลตอบคำถามอะไรได้ การเริ่มจากหน้าว่างคือจุดที่คนติด
- คำแนะนำที่มาจากโปรไฟล์ช่วยกันขอสิ่งที่ข้อมูลไม่มี (เช่น ขอ "ยอดขายรายเดือน" จากตารางที่ไม่มีวันที่)
- ผู้เชี่ยวชาญยังพิมพ์เองได้ ไม่เสียอะไร

## 3. คำแนะนำที่อ้างอิงจาก Dataset จริง

### 3.1 หลักการ: ระบบสร้างคำแนะนำจากโปรไฟล์ด้วยกฎก่อน แล้ว AI เสริมทีหลัง

โปรไฟล์ที่ระบบมีอยู่แล้วต่อคอลัมน์ [มีแล้ว] (`profile_dataframe` `dashboard_data.py:97-114`): ชื่อ, ชนิด (numeric / categorical / date / text), จำนวนค่าไม่ซ้ำ, % ค่าว่าง, ช่วงต่ำสุด-สูงสุดของตัวเลขและวันที่ และจำนวนแถวของตาราง ข้อมูลเหล่านี้พอสร้างคำแนะนำได้โดยไม่ต้องเรียก AI

**ข้อเสนอสองชั้น [ข้อเสนอ]:**

| ชั้น | ทำอะไร | ข้อดี |
|---|---|---|
| ชั้น 1 กฎ (deterministic) | ฟังก์ชันล้วนอ่านโปรไฟล์ แล้วคืนรายการคำแนะนำพร้อม spec ชิ้นส่วนที่ผ่าน whitelist แล้ว | เร็ว ฟรี ทำงานโดยไม่มี AI ผลซ้ำได้ ไม่แนะนำสิ่งที่ทำไม่ได้ |
| ชั้น 2 AI (ทางเลือก) | ส่งโปรไฟล์ (ไม่มีค่าข้อมูล) ให้ Groq จัดอันดับและเรียบเรียงคำแนะนำชั้น 1 เป็นภาษาธุรกิจตามกลุ่มผู้ใช้ แล้วตรวจซ้ำด้วย `validate_spec` | ภาษาเป็นธรรมชาติ เลือกลำดับตามกลุ่มผู้ใช้ |

ถ้าชั้น 2 ล้ม ผู้ใช้ยังได้ชั้น 1 เหมือนกับที่การสร้างแดชบอร์ดมีโหมดกฎสำรองอยู่แล้ว

### 3.2 กฎการสร้างคำแนะนำ [ข้อเสนอ]

**คอลัมน์ที่ต้องตัดออกก่อน:**

| รหัส | เงื่อนไข | เหตุผล |
|---|---|---|
| E1 | ตัวเลขที่ค่าไม่ซ้ำ ≥ 90% ของแถว หรือมี ≥ 9 หลัก | เป็นรหัส ไม่ใช่ปริมาณ ใช้ตรรกะเดียวกับ `_looks_like_identifier` `dashboard_llm.py:110-117` ที่มีอยู่แล้ว |
| E2 | ชนิด text | เช่น ชื่อลูกค้า รหัสสินค้า ไม่เหมาะแกนกราฟ |
| E3 | วันที่ที่ค่าไม่ซ้ำ ≤ 1 | เช่น `updated_at` ไม่มีแนวโน้มให้ดู |
| E4 | % ค่าว่าง > 50 | ข้อมูลไม่พอ |
| E5 | คอลัมน์เทคนิค เช่น `row_hash` `dirty_row_id` | ปัจจุบันระบบตัดแค่ `run_id`, `ingest_id`, `__index_level_0__` (`dashboard_data.py:23`) ต้องเพิ่ม |

**กฎคำแนะนำ:**

| รหัส | เงื่อนไขจากโปรไฟล์ | คำแนะนำ | วิดเจ็ตที่ระบบรองรับแล้ว |
|---|---|---|---|
| R1 แนวโน้ม | มีวันที่ ระบบเลือกหน่วยเวลา (วัน/สัปดาห์/เดือน/ไตรมาส/ปี) ที่ทำให้ได้ ≥ 3 ช่วง | "แนวโน้ม {measure} รายเดือน" (หรือรายสัปดาห์ตามช่วงข้อมูล) | line + time_grain |
| R2 อันดับและเปรียบเทียบ | หมวดหมู่ที่ค่าไม่ซ้ำ 2 ถึง 50 | "{measure} ตาม {หมวด}" และถ้ามากกว่า 10 ค่า "10 {หมวด} ที่ {measure} สูงสุด" | bar, sort desc, limit 10 (สูงสุด 20) |
| R3 สัดส่วน | หมวดหมู่ที่ค่าไม่ซ้ำ 2 ถึง 8 และ measure เป็นผลรวมหรือจำนวน (สัดส่วนจึงมีความหมาย ค่าเฉลี่ยไม่ใช้) | "สัดส่วน {measure} ตาม {หมวด}" | donut (สูงสุด 8) |
| R4 เทียบช่วง | วันที่ที่มี ≥ 2 ช่วง | "{measure} ช่วงล่าสุดเทียบช่วงก่อนหน้า" | kpi + compare (วัน/สัปดาห์/เดือน/ไตรมาส/ปี) |
| R5 แยกสองมิติ | หมวดหมู่ 2 คอลัมน์ (ตัวหนึ่ง ≤ 8) | "{measure} ตาม {หมวด A} แยกตาม {หมวด B}" | bar + group_by + stacked |
| R6 ตัวกรอง | หมวดหมู่ ≤ 50 ค่า, วันที่ | "เพิ่มตัวกรอง {คอลัมน์}" | filters (สูงสุด 6) |
| R7 สรุปตัวเลข | ชุดที่ไม่มีวันที่หรือหมวดหมู่ | KPI ค่าเฉลี่ย/ต่ำสุด/สูงสุด | kpi |
| R8 สุขภาพข้อมูล | คอลัมน์ที่ค่าว่าง ≥ 5% หรือรอบตรวจล่าสุดต่ำกว่าเกณฑ์ | "ตรวจค่าว่างของ {คอลัมน์}" / "ดูแนวโน้มคุณภาพของตารางนี้" | table / ชุด `_quality_runs` ที่มีอยู่แล้ว |

**การเลือก measure เมื่อยังไม่มี Semantic Layer:** ใช้คอลัมน์ตัวเลขที่ชื่อมีคำเช่น sales, revenue, amount, total, profit, score, ยอดขาย, รวม ก่อน ถ้าไม่เจอใช้ตัวเลขตัวแรกที่ไม่ถูกตัดโดย E1 เมื่อทำ Semantic Layer (หัวข้อ 7) แล้วให้ใช้ `role = measure` และ `label` แทน

**จำกัดไม่เกิน 6 คำแนะนำ** เลือกให้ครอบคลุมวิดเจ็ตหลายแบบ ไม่ซ้ำแบบเดียวกัน

### 3.3 ตัวอย่างจากข้อมูลจริงในระบบ

**ก) `global_ecommerce_sales`** (2,000 แถว, `Order_Date` 2023-01-02 ถึง 2025-12-31)

| คอลัมน์ | ชนิด | ค่าไม่ซ้ำ |
|---|---|---|
| Order_Date | date | 907 |
| Region / Product_Category / Customer_Segment / Payment_Method | categorical | 5 / 4 / 3 / 4 |
| Country / Product_Name | categorical | 20 / 40 |
| Total_Sales, Profit, Quantity, Shipping_Cost | numeric | |
| Order_ID, Customer_Name | text | ตัดออก (E2) |

คำแนะนำที่กฎจะสร้าง:
1. แนวโน้ม Total_Sales รายเดือน (R1)
2. Total_Sales ปีล่าสุดเทียบปีก่อนหน้า (R4 ช่วงข้อมูลครอบคลุม 3 ปี)
3. 10 Product_Name ที่ Total_Sales สูงสุด (R2 มี 40 ค่า)
4. สัดส่วน Total_Sales ตาม Region (R3 มี 5 ค่า)
5. Profit แยกตาม Country (R2 มี 20 ค่า)
6. Total_Sales ตาม Customer_Segment แยกตาม Payment_Method (R5)

หมายเหตุ: ข้อมูลครอบคลุมปี 2023 ถึง 2025 ดังนั้นคำแนะนำ "เปรียบเทียบปี 2025 กับ 2026" จะไม่ถูกสร้าง เพราะไม่มีข้อมูลปี 2026 นี่คือข้อดีของการอ้างอิงช่วงวันที่จริง

**ข) `olist_products_dataset`** (21,767 แถว, **ไม่มีคอลัมน์วันที่ ไม่มียอดขาย**)

คอลัมน์: product_id (text), product_category_name (categorical 72 ค่า), ตัวเลข 7 คอลัมน์ (น้ำหนัก, ขนาด, จำนวนรูป ฯลฯ)

คำแนะนำที่กฎจะสร้าง:
1. 10 หมวดสินค้าที่มีจำนวนสินค้ามากที่สุด (R2)
2. น้ำหนักเฉลี่ย (product_weight_g) แยกตามหมวดสินค้า 10 อันดับ (R2)
3. สัดส่วนสินค้าตามจำนวนรูป (product_photos_qty มี 5 ค่า, R3)
4. KPI ค่าเฉลี่ยน้ำหนักและขนาด (R7)

จะไม่มีคำแนะนำแนวโน้มหรือเทียบช่วง เพราะไม่มีวันที่ ตรงข้ามกับตัวอย่างตายตัวตอนนี้ที่โชว์ "ยอดขายรายเดือน" ให้ตารางนี้

**ค) `student_course_scores`** (9,370 แถว) คอลัมน์ `dirty_row_id`, `record_id`, `student_id` เป็นตัวเลขที่ค่าไม่ซ้ำ = จำนวนแถวพอดี ระบบจะตัดออกด้วย E1 ส่วน `updated_at` มีค่าเดียวจึงตัดด้วย E3

1. คะแนนเฉลี่ย (score) แยกตาม course (R2 มี 5 ค่า ใช้กราฟแท่งเพราะเป็นค่าเฉลี่ย)
2. ชั่วโมงเรียนเฉลี่ยแยกตาม course
3. คะแนนเฉลี่ยของ semester ล่าสุดเทียบก่อนหน้า (R4 มี 2 ช่วง)
4. สัดส่วนจำนวนนักเรียนตาม course (R3 เป็นจำนวนนับ จึงใช้สัดส่วนได้)

**ง) `grocery_sales`** ชื่อคอลัมน์เป็นภาษาไทย (วันที่, รายการสินค้า, จำนวน, ราคาต่อหน่วย, ยอดขายรวม) วันที่ 2026-06-01 ถึง 2026-07-30

1. แนวโน้ม ยอดขายรวม รายสัปดาห์ (R1 ช่วงราว 2 เดือน จึงเหมาะรายสัปดาห์ ไม่ใช่รายเดือน)
2. 10 รายการสินค้าที่ยอดขายรวมสูงสุด (R2 มี 23 ค่า)
3. "ตรวจค่าว่างของ ยอดขายรวม (ว่าง 2.33%)" (R8)

ตัวอย่างนี้แสดงว่าวิธีนี้ใช้ได้กับชื่อคอลัมน์ภาษาไทย เพราะมาจากโปรไฟล์ ไม่ใช่การจับคีย์เวิร์ดภาษาอังกฤษอย่างเดียว

### 3.4 ข้อกำกับความปลอดภัย

- คำแนะนำชั้น 1 คือ spec ชิ้นส่วนที่ผ่าน whitelist เดิม จึงสร้างแล้วใช้ได้แน่นอน ไม่เสี่ยงที่ AI ตอบสเปกที่รันไม่ได้
- ชั้น 2 ส่งเฉพาะโปรไฟล์ ไม่ส่งค่าข้อมูล ตรงกับกติกาเดิมของ `profile_for_prompt`
- ระบบอ่านค่าหมวดหมู่เองไม่ได้ในฝั่ง AI (ไม่ส่งไป) คำแนะนำจึงเขียนจาก "ชื่อคอลัมน์" เช่น "10 Product_Name ที่..." ไม่ใช่ชื่อสินค้าจริง

## 4. ผู้ใช้ Dashboard และ Role

### 4.1 สถานะจริงของระบบ

- **ระบบ login มีบัญชีผู้ดูแลเดียว** (`auth.py:112-113` อ่าน `ADMIN_USERNAME` และ `ADMIN_PASSWORD`) ไม่มีระบบ role และสิทธิ์แยกตามผู้ใช้ [มีแล้ว ตามที่เป็นอยู่]
- ตัวเลือก "ผู้ใช้แดชบอร์ด" 3 ค่า (Business User, Data Analyst, Management) เป็นแค่ **คำใบ้ให้ AI** ผ่านบรรทัดเดียวใน system prompt (`dashboard_llm.py:69`) ไม่ใช่สิทธิ์การเข้าถึง

ดังนั้น "Role" ในที่นี้หมายถึง **ประเภทผู้อ่านหรือวัตถุประสงค์ของแดชบอร์ด** ไม่ใช่การแยกสิทธิ์ผู้ใช้ ถ้าต้องการสิทธิ์จริงต้องทำระบบ RBAC แยก ซึ่งอยู่นอกขอบเขตนี้ (แผน Semantic Layer ก็ระบุว่ายังไม่ทำ)

### 4.2 ข้อเสนอ: เพิ่มหนึ่งตัวเลือก ไม่ต้องเพิ่มหลายตัว [ข้อเสนอ]

| ตัวเลือก | สถานะ | แนะนำ |
|---|---|---|
| Business User | มีแล้ว | คงไว้ เปลี่ยนป้ายเป็น "ผู้ใช้ธุรกิจ" |
| Data Analyst | มีแล้ว | คงไว้ |
| Management | มีแล้ว | คงไว้ และ **รวม Executive เข้าด้วยกัน** เพราะเนื้อหาเหมือนกัน (KPI เด่น แนวโน้ม ไม่มีตารางกว้าง) |
| **Data Steward / Data Engineer** | ไม่มี | **เพิ่ม** ใช้ชื่อ "ดูแลคุณภาพข้อมูล" |

เหตุผลที่เพิ่มตัวเดียว: ตรงกับแกนของ SDOQAP และมีข้อมูลรองรับอยู่แล้ว คือชุด `_quality_runs` (ประวัติผลตรวจทุกรอบ) ที่หน้านี้ใช้ได้อยู่แล้ว ผู้ดูแลข้อมูลต้องการดูแนวโน้มคะแนน แถวที่ถูกกักกัน และคอลัมน์ที่ว่าง ไม่ใช่ยอดขาย

**หลักฐานจริงว่าทำไมต้องมี:** ในตาราง `pg_student_scores` ที่อยู่ใน active ค่า `record_id` ไม่ซ้ำเพียง 9,349 จาก 9,441 แถว (มีแถวซ้ำ) และ `score` สูงสุดเท่ากับ 101 ซึ่งอาจเกินช่วงคะแนนปกติ ผู้ดูแลข้อมูลควรเห็นสิ่งนี้บนแดชบอร์ดคุณภาพของตารางนั้นเอง

### 4.3 แต่ละกลุ่มได้อะไรต่างกัน

| กลุ่ม | วิดเจ็ตที่เน้น | คำแนะนำที่จัดอันดับขึ้นก่อน | สถานะ |
|---|---|---|---|
| ผู้ใช้ธุรกิจ | สมดุล KPI + กราฟ | R2 อันดับ, R3 สัดส่วน | ผ่านคำใบ้ใน prompt [มีแล้ว] |
| Data Analyst | แตกมิติ + ตารางละเอียด | R5 แยกสองมิติ, R6 ตัวกรอง | ผ่านคำใบ้ใน prompt [มีแล้ว] |
| Management | KPI หัวข้อ + เทียบช่วง + แนวโน้ม ไม่มีตารางกว้าง | R4 เทียบช่วง, R1 แนวโน้ม | ผ่านคำใบ้ใน prompt [มีแล้ว] |
| ดูแลคุณภาพข้อมูล | คะแนนคุณภาพ แถวที่กักกัน ค่าว่างต่อคอลัมน์ | R8 สุขภาพข้อมูล | [ข้อเสนอ] |

**สิ่งที่ต้องแก้ควบคู่:** ให้การจัดอันดับคำแนะนำ (ชั้น 1) และโหมดกฎอัตโนมัติ `fallback_spec` ใช้กลุ่มผู้ใช้ด้วย ปัจจุบันมันไม่ใช้ (ปัญหาข้อ 3 ในหัวข้อ 2.1)

## 5. ปรับ Dashboard ด้วย AI: คำแนะนำที่เข้าใจบริบท

### 5.1 สถานะจริง

- AI **อ่านบริบทอยู่แล้ว** ตอนปรับ: `build_refine_messages` ส่ง `current_spec` + โปรไฟล์ + คำสั่งไป (`dashboard_llm.py:139-143`) [มีแล้ว]
- สิ่งที่ขาดคือ **ผู้ใช้ไม่เห็นคำแนะนำ** เพราะปุ่มตัวอย่างเป็นข้อความตายตัว 5 ข้อ (`RefinePanel.jsx:3-9`)

### 5.2 ข้อเสนอ: วิเคราะห์ช่องว่างระหว่าง spec กับโปรไฟล์ด้วยโค้ด [ข้อเสนอ]

ระบบมีทั้ง spec ปัจจุบัน (รู้ว่าใช้คอลัมน์ไหนไปแล้ว) และโปรไฟล์ (รู้ว่ามีคอลัมน์อะไรบ้าง) จึงหา "สิ่งที่ยังไม่ได้ใช้" ได้ด้วยโค้ด ไม่ต้องเรียก AI:

| รหัส | เงื่อนไข | คำแนะนำที่แสดง |
|---|---|---|
| G1 | คอลัมน์หมวดหมู่ที่ไม่มีตัวกรอง (และไม่เกิน 6 ตัวกรอง) | "เพิ่มตัวกรอง {คอลัมน์}" |
| G2 | คอลัมน์ measure ที่ยังไม่มี KPI | "เพิ่ม KPI {agg} ของ {คอลัมน์}" |
| G3 | มีวันที่แต่ยังไม่มีกราฟเส้น/พื้นที่ | "เพิ่มแนวโน้ม {measure} ตาม {วันที่}" |
| G4 | มีวันที่ ≥ 2 ช่วง แต่ KPI ไม่มี compare | "แสดง {KPI} เทียบช่วงก่อนหน้า" |
| G5 | กราฟแท่งที่ x มี ≤ 8 ค่า | "เปลี่ยน '{ชื่อกราฟ}' เป็นกราฟสัดส่วน" |
| G6 | กลุ่มผู้ใช้ Management แต่มีตารางกว้างอยู่ | "ลบตารางรายละเอียดให้เหมาะกับผู้บริหาร" |
| G7 | หลังปรับแล้ว ยังไม่มี R8 และรอบคุณภาพต่ำกว่าเกณฑ์ | "เพิ่มกล่องสรุปคุณภาพข้อมูล" |

**ตัวอย่างจริง:** สมมติแดชบอร์ดของ `global_ecommerce_sales` มี KPI Total_Sales กับกราฟแท่งตาม Country และตัวกรอง Region ระบบจะแนะนำ:
- "เพิ่มตัวกรอง Product_Category" (G1)
- "เพิ่ม KPI ค่าเฉลี่ยของ Profit" (G2)
- "เพิ่มแนวโน้ม Total_Sales ตาม Order_Date" (G3)
- "แสดง Total_Sales เทียบปีก่อนหน้า" (G4)

และจะไม่แนะนำ "เพิ่ม Filter จังหวัด" เพราะไม่มีคอลัมน์จังหวัด

**ข้อจำกัดที่ต้องบอกผู้ใช้ตรง ๆ:** ระบบปัจจุบันเทียบได้แค่ "ช่วงล่าสุดกับช่วงก่อนหน้า" (`compare`) เปรียบเทียบสองปีที่ระบุเองต้องใช้ตัวกรองช่วงวันที่ทำทีละช่วง และยังไม่มี KPI อัตราส่วน (กำไรต่อยอดขาย) จนกว่าจะทำ Semantic Layer

### 5.3 การใช้ AI ชั้นเสริม [ข้อเสนอ]

เมื่อผู้ใช้พิมพ์เอง AI ทำงานตามเดิม เพิ่ม: ส่ง "รายการช่องว่าง G1 ถึง G7" ไปพร้อม prompt ปรับ เพื่อให้ AI ตีความคำสั่งกำกวม เช่น "ทำให้ดูง่ายขึ้น" ได้ตรงกับสิ่งที่ข้อมูลรองรับ

## 6. ข้อเสนอ Final Design: Flow ที่แนะนำ

**หลักการแบ่งหน้าที่:** ระบบรับผิดชอบ **ตัวเลขและความถูกต้องของโครงสร้าง** AI รับผิดชอบ **ข้อเสนอและภาษา** คนรับผิดชอบ **ความหมายทางธุรกิจและการตัดสินใจสุดท้าย**

| ขั้น | ระบบ (System) | AI | ผู้ใช้ตัดสินใจ |
|---|---|---|---|
| 1. เลือก Dataset | แสดงเฉพาะตารางที่ผ่านการตรวจรายแถว เรียงตามอัปเดตล่าสุด พร้อมป้ายคะแนนคุณภาพ [มีแล้ว] | ไม่เกี่ยว | เลือกตาราง โดยรู้ระดับความน่าเชื่อถือก่อน |
| 2. Profiling | คำนวณโปรไฟล์ด้วย pandas เตือนเมื่อคุณภาพต่ำกว่าเกณฑ์และบอกจำนวนแถวที่กักกัน [มีแล้ว] ตรวจคอลัมน์ที่ว่าง/รหัส/ช่วงวันที่ [ข้อเสนอ] | ไม่เกี่ยว | ตรวจว่าข้อมูลดูสมเหตุสมผล |
| 3. วิเคราะห์ Dataset | สร้างคำแนะนำชั้น 1 ด้วยกฎ R1 ถึง R8 พร้อม spec ที่ผ่าน whitelist [ข้อเสนอ] | (ทางเลือก) จัดอันดับและเรียบเรียงภาษาตามกลุ่มผู้ใช้ [ข้อเสนอ] | ไม่ต้องทำอะไร |
| 4. เลือกสิ่งที่อยากเห็น | แสดงการ์ดคำแนะนำ [ข้อเสนอ] | ไม่เกี่ยว | เลือก 1 ถึง N การ์ด และ/หรือพิมพ์เอง เลือกกลุ่มผู้ใช้ |
| 5. สร้างฉบับร่าง | ตรวจ spec ด้วย whitelist คำนวณทุกวิดเจ็ตด้วย pandas ใช้โหมดกฎถ้า AI ไม่พร้อม [มีแล้ว] | ออกแบบ spec: เลือกกราฟ แกน จัดวาง [มีแล้ว] | รอ |
| 6. ตรวจและแก้ | กรอง/เจาะลึกด้วยการคลิก คำนวณใหม่ แสดง "สิ่งที่เปลี่ยน" ด้วย `diff_specs` [มีแล้ว] คำแนะนำปรับจากช่องว่าง G1 ถึง G7 และ undo [ข้อเสนอ] | แก้ spec ตามคำสั่ง [มีแล้ว] | **ตัดสินใจว่าแดชบอร์ดนี้ถูกต้องตามความหมายธุรกิจหรือไม่** แล้วเก็บหรือแก้ต่อ |
| 7. บันทึก | เก็บ spec (ไม่เก็บตัวเลข) ใน Elasticsearch [มีแล้ว] เจ้าของและสิทธิ์ [ข้อเสนอ] | ไม่เกี่ยว | ตั้งชื่อ ยืนยันบันทึก |

| 3. กลุ่มผู้ใช้ใหม่ | เพิ่ม "ดูแลคุณภาพข้อมูล" + ให้ `fallback_spec` ใช้กลุ่มผู้ใช้ | กลาง | เชื่อมกับแกนหลักของ SDOQAP |
| 4. AI ชั้นเสริม | จัดอันดับ/เรียบเรียงคำแนะนำด้วย Groq (ตรวจซ้ำด้วย validate_spec) | กลาง | ภาษาเป็นธรรมชาติขึ้น |
| 5. Semantic Layer | ทำตาม spec ที่มีอยู่แล้ว ได้ role/หน่วย/สกุลเงิน/KPI อัตราส่วน/ซ่อนข้อมูลส่วนบุคคล | ใหญ่ | วางรากให้ระยะ 1 ถึง 4 ฉลาดขึ้น |
| 6. ต่อกับเครื่องมือ BI | ส่งออก spec หรือข้อมูลที่กรองแล้ว | กลาง | เปลี่ยนจากคู่แข่งเป็นส่วนเสริมของทีม BI |

**หมายเหตุสำคัญ:** Semantic Layer มี spec และแผนเขียนไว้แล้ว (`docs/superpowers/specs/2026-10-02-semantic-layer-design.md`, `docs/superpowers/plans/2026-10-02-semantic-layer.md`) แต่ **ไม่พบโค้ดที่สร้าง index `sdoqap_semantic_layer` ในโค้ดของระบบ** (ขั้นตอนย่อย 60 ข้อในแผนยังไม่ถูกติ๊กเสร็จสักข้อ) ระยะ 1 ถึง 4 ออกแบบให้ทำได้โดยไม่ต้องรอ และเมื่อทำระยะ 5 แล้วให้สลับไปใช้ role/label จริงแทนการเดาจากชื่อคอลัมน์

## 8. คำถามที่กรรมการอาจถาม

| คำถาม | คำตอบที่ตรงกับระบบ |
|---|---|
| บริษัทมีทีม BI แล้ว ฟังก์ชันนี้มีไว้ทำไม | ช่วยให้ทีมได้ฉบับร่างเร็วขึ้นจากข้อมูลที่ผ่านการตรวจ และบอกระดับความน่าเชื่อถือของข้อมูลก่อนใช้ ซึ่งเครื่องมือ BI ทั่วไปไม่มี ทีมยังเป็นผู้ตัดสินและเจ้าของแดชบอร์ดสุดท้าย |
| AI คิดตัวเลขเองหรือเปล่า | ไม่ AI ออกแบบ spec ตัวเลขคำนวณด้วยโค้ด pandas จากข้อมูลจริงทุกตัว |
| ข้อมูลออกไปให้ AI ภายนอกไหม | ส่งแค่ชื่อคอลัมน์ ชนิด และสถิติ ไม่ส่งแถวและไม่ส่งค่าหมวดหมู่ ข้อความที่ผู้ใช้พิมพ์ถูกส่งตามที่พิมพ์ จึงควรเตือนผู้ใช้ไม่ให้ใส่ข้อมูลลับ |
| ถ้า AI ล่มหรือไม่มี key | สร้างแดชบอร์ดด้วยโหมดกฎอัตโนมัติได้ แต่การปรับด้วย AI ใช้ไม่ได้ |
| ข้อมูลใน active ถูกต้อง 100% ไหม | ไม่ เป็นข้อมูลที่ผ่านกฎตรวจรายแถว และยังมีรอบที่คะแนนต่ำกว่าเกณฑ์เข้ามาได้ จึงมีป้ายคะแนนและกล่องเตือนให้ผู้ใช้เห็น |
| ทำไมไม่ใช้ Power BI อย่างเดียว | ใช้ร่วมกันได้ จุดต่างคือ Create Dashboard เกาะอยู่กับผลตรวจคุณภาพของ pipeline เดียวกัน (ข้อเสนอระยะ 6 จะทำให้ส่งต่อให้ BI ได้) |

## ภาคผนวก: สิ่งที่มีจริงวันนี้ เทียบกับข้อเสนอ

**มีแล้วและตรวจจากโค้ด:** เลือกเฉพาะตารางใน `/data/active` | โปรไฟล์คอลัมน์ | สร้าง spec ด้วย Groq พร้อมโหมดกฎสำรอง | ตรวจ spec ด้วย whitelist | คำนวณด้วย pandas | ตัวกรองและเจาะลึกด้วยการคลิก | ปรับด้วย AI พร้อมสรุปสิ่งที่เปลี่ยน | บันทึก เปิด ลบ | ป้ายคะแนนคุณภาพ กล่องเตือน และเรียงตามอัปเดตล่าสุด | คำแนะนำจากโปรไฟล์กฎ R1 ถึง R5 และ R7 | คำบรรยายหน้าและป้ายฉบับร่าง | คำแนะนำปรับตามช่องว่างกฎ G1 ถึง G6 | ปุ่มย้อนกลับหลังปรับด้วย AI (ระยะ 2) | กลุ่มผู้ใช้ "ดูแลคุณภาพข้อมูล" กฎ R8 และโหมดกฎอัตโนมัติที่ใช้กลุ่มผู้ใช้ | การคำนวณ count_missing (ระยะ 3) | ปุ่มให้ AI จัดลำดับและเรียบเรียงคำแนะนำ (ตรวจซ้ำว่าเลือกได้เฉพาะรายการของกฎ) และการส่งรายการสิ่งที่แดชบอร์ดยังขาดไปพร้อม prompt ปรับ (ระยะ 4)

**ยังไม่มี (ข้อเสนอทั้งหมดในเอกสารนี้):** คำแนะนำกฎ R6 | คำแนะนำปรับกฎ G7 | บันทึกเป็นฉบับใหม่ | เจ้าของและสิทธิ์ของแดชบอร์ด | ระบบ role จริง | Semantic Layer | KPI อัตราส่วน | การค้นหา Insight | การส่งออกไปเครื่องมือ BI
